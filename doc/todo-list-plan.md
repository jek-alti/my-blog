# 구현 계획: To-Do 리스트 앱

> **v2 — Codex 검증 반영.** Codex 리뷰에서 FAIL 판정을 받은 6가지 문제(Review·Embed 단계 누락, 팔레트 연동 방식 불명확, localStorage 처리 미구체화, 작업 1 규모 오산정, 접근성 기준 부재, 작업 6 의존성 어긋남)를 모두 반영해 재작성했다.

## 개요

블로그 웹앱 포트폴리오에 추가할 간단한 To-Do 리스트 앱을 만든다. 순수 HTML/CSS/JS로 구현하며, 데이터는 서버 없이 브라우저 localStorage에 저장한다. 블로그의 색상 팔레트를 따르고, 모바일에서도 정상 동작해야 하며, 화면에 사용법 안내 문구를 포함한다. CLAUDE.md가 요구하는 Plan→Build→**Review→Embed** 전체 흐름을 계획에 포함한다.

## 아키텍처 결정 사항

- 프레임워크 없이 순수 HTML/CSS/JS 사용 — 블로그 웹앱 규칙(외부 라이브러리 최소화) 준수
- **팔레트 연동 방식(확정):** 루트 `css/style.css`를 직접 링크하지 않고, `apps/pixel-art`·`apps/2048`과 동일한 방식으로 `apps/todo-list/style.css`에 `:root`를 정의해 루트 팔레트와 같은 값(`--bg`, `--text`, `--accent` 등)을 로컬로 선언한다. 기존 앱들이 이미 이 패턴을 쓰고 있어 저장소 관례와 일치한다.
- **localStorage 스키마(확정):** 키 `todo-list-tasks`, 값은 `[{ id, text, completed }]` 배열(JSON). `apps/pixel-art/app.js`의 저장/복원 패턴(try/catch로 감싸고, 복원 시 형식이 다르면 무시)을 그대로 따른다.
- 사용자 입력은 `innerHTML`이 아닌 `textContent`로 렌더링 — XSS 방지
- 모든 상호작용 요소는 네이티브 HTML 컨트롤(`input`, `button`, `label`)을 사용해 키보드 조작과 스크린리더 호환을 기본으로 확보한다.

## 작업 목록

### 1단계: 기반 구축

#### 작업 1: 스캐폴딩 + 추가·표시·저장 + 팔레트 연동 + 사용법 안내

**설명:** `apps/todo-list/` 아래 3개 파일을 만들어 입력→추가→목록 표시→localStorage 저장까지의 기본 흐름을 구현하고, 팔레트 연동과 화면 사용법 안내까지 이 단계에서 함께 끝낸다. (Codex 피드백 #2, #3, #4, #6 반영: 팔레트 방식 확정, 저장소 스키마 확정, 규모 재산정, 사용법 안내를 초기 단계로 이동)

**수용 기준:**
- [ ] 입력 후 추가 시 목록에 즉시 표시됨
- [ ] 새로고침해도 목록이 유지됨
- [ ] 빈 입력은 추가되지 않음
- [ ] 입력 필드에 `label` 또는 `aria-label`이 있어 스크린리더로 용도를 알 수 있음
- [ ] `apps/todo-list/style.css`의 `:root`에 루트 `css/style.css`와 동일한 값의 `--bg`, `--text`, `--accent`(필요 시 `--border`, `--surface` 등)를 정의해 사용 — 색상 하드코딩 없음
- [ ] 블로그의 각 테마에서 모두 배경/텍스트/강조색이 올바르게 나타남
- [ ] 화면에 사용법 안내 문구(추가·완료·삭제·필터 방법)가 바로 보이고, 모바일 너비에서도 잘리지 않음

**저장소 처리 세부사항:**
- 저장 키: `todo-list-tasks`
- 데이터 형식: `[{ id: string, text: string, completed: boolean }]`
- `save()`/`load()`는 `try/catch`로 감싸 저장 실패(프라이빗 모드 등)를 조용히 무시하지 않고, 실패 시 화면에 비침해적 안내 문구를 표시한다
- `load()` 시 JSON 파싱 실패 또는 배열/필드 형식이 다른 데이터는 무시하고 빈 목록으로 폴백한다 (임의 문자열 주입 방지)

**검증:**
- [ ] 브라우저에서 직접 추가 → 새로고침 → 유지 확인
- [ ] 콘솔에 에러 없음
- [ ] 개발자도구에서 `localStorage["todo-list-tasks"]` 값 확인
- [ ] 개발자도구에서 손상된 JSON을 수동으로 넣은 뒤 새로고침해도 앱이 깨지지 않고 빈 목록으로 폴백하는지 확인
- [ ] 모바일 뷰(375px)에서 입력창·안내 문구가 잘리지 않는지 확인
- [ ] 테마 전환 후에도 색상이 올바르게 반영되는지 확인

**의존성:** 없음

**영향받는 파일:**
- `apps/todo-list/index.html`
- `apps/todo-list/style.css`
- `apps/todo-list/script.js`

**예상 규모:** M (파일 3개 — 마크업·스타일·저장/렌더링 로직이 함께 들어가는 기반 슬라이스라 S가 아닌 M으로 재산정)

## 작업 규모 산정 기준

| 규모 | 파일 수 | 예시 |
|---|---|---|
| XS | 1개 | 체크박스 완료 처리 같은 단일 동작 추가 |
| S | 1~2개 | 필터링·리뷰 문서 작성 같은 기능 하나 |

## 위험 요소와 대응 방안

| 위험 | 영향도 | 대응 방안 |
|---|---|---|
| localStorage 미지원/차단 또는 저장된 JSON 손상 | 중 | 키 `todo-list-tasks`, 형식 `[{id, text, completed}]`로 고정하고 `try/catch`로 저장/복원을 감싼다. 형식이 다르면 빈 목록으로 폴백하고, 저장 실패 시 화면에 안내 문구를 표시한다 (작업 1에서 구현·검증) |
| 사용자 입력을 그대로 HTML에 삽입 시 XSS | 높음 | `innerHTML` 대신 `textContent` 사용해 입력값 이스케이프 |
| 접근성 기준 누락 시 키보드/스크린리더 사용자 배제 | 중 | (Codex 리뷰로 발견) 라벨링된 네이티브 컨트롤, 키보드 오퍼러블 필터, 포커스 관리, 빈 상태 안내를 작업 1~5의 수용 기준에 명시적으로 포함 |
| 여러 탭에서 동시 편집 시 데이터 불일치 | 낮음 | 이번 범위에서는 대응하지 않음 — 열린 질문으로 남김 |

## 열린 질문

- 앱 이름과 디자인 톤을 어떻게 정할지 (사람 결정 필요)
- 마감일·우선순위 등 확장 기능을 이번 범위에 포함할지
- 여러 탭 동시 사용 시나리오까지 지원해야 하는지
- 앱 카드에 미리보기 이미지를 쓸지, iframe으로 바로 임베드할지 (Embed 단계 진행 전 결정 필요)

## 병렬화 가능 지점

작업 3(삭제)과 작업 4(필터링 준비)는 작업 2 완료 후 서로 독립적으로 병렬 진행 가능하다. 작업 5(반응형 마무리)는 작업 1~4가 모두 끝난 뒤 전체 화면을 대상으로 점검해야 하므로 병렬화하지 않는다. Review(작업 6)는 Build(작업 1~5)와 반드시 분리된 관점에서 진행해야 하므로 같은 에이전트가 이어서 하지 않는다.
