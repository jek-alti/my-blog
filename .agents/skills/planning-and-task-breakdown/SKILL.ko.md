# 계획 수립과 작업 분해 (Planning and Task Breakdown)

> 이 문서는 `planning-and-task-breakdown` 스킬(원본: `SKILL.md`)의 한국어 번역본입니다. 원본이 갱신되면 이 번역본은 오래된 내용일 수 있습니다.

## 개요

작업을 명시적인 수용 기준(acceptance criteria)을 가진, 작고 검증 가능한 단위로 분해한다. 작업 분해를 잘하느냐 못하느냐가 곧 "작업을 안정적으로 완수하는 에이전트"와 "뒤엉킨 결과물을 만드는 에이전트"의 차이다. 모든 작업은 한 번의 집중 세션 안에서 구현·테스트·검증할 수 있을 만큼 작아야 한다.

## 언제 사용하는가

- 스펙이 있고, 이를 구현 가능한 단위로 나눠야 할 때
- 작업이 너무 크거나 모호해서 시작하기 어려울 때
- 여러 에이전트나 세션에 걸쳐 작업을 병렬화해야 할 때
- 사람에게 작업 범위를 전달해야 할 때
- 구현 순서가 명확하지 않을 때

**사용하지 않아도 되는 경우:** 범위가 명확한 단일 파일 변경, 또는 스펙 자체에 이미 잘 정의된 작업 목록이 있는 경우.

## 계획 수립 절차

### 1단계: 계획 모드(Plan Mode) 진입

코드를 작성하기 전, 읽기 전용 모드로 동작한다:

- 스펙과 관련된 코드베이스 부분을 읽는다
- 기존 패턴과 관례를 파악한다
- 컴포넌트 간 의존관계를 매핑한다
- 위험 요소와 불확실한 부분을 기록한다

**계획 단계에서는 절대 코드를 작성하지 않는다.** 결과물은 `tasks/plan.md`에 저장되는 계획 문서와 `tasks/todo.md`에 저장되는 작업 목록이며, 구현 코드가 아니다.

### 2단계: 의존성 그래프 파악

무엇이 무엇에 의존하는지 매핑한다:

```
데이터베이스 스키마
    │
    ├── API 모델/타입
    │       │
    │       ├── API 엔드포인트
    │       │       │
    │       │       └── 프론트엔드 API 클라이언트
    │       │               │
    │       │               └── UI 컴포넌트
    │       │
    │       └── 검증(validation) 로직
    │
    └── 시드 데이터 / 마이그레이션
```

구현 순서는 의존성 그래프를 따라 아래에서 위로 진행한다: 기반(foundation)부터 먼저 만든다.

### 3단계: 수직으로 슬라이스하기

DB 전체를 만들고, 그다음 API 전체를 만들고, 그다음 UI 전체를 만드는 대신 — 한 번에 하나의 완전한 기능 경로(feature path)를 끝까지 만든다:

**나쁜 예 (수평 슬라이싱):**
```
작업 1: 데이터베이스 스키마 전체 구축
작업 2: API 엔드포인트 전체 구축
작업 3: UI 컴포넌트 전체 구축
작업 4: 전부 연결하기
```

**좋은 예 (수직 슬라이싱):**
```
작업 1: 사용자가 계정을 생성할 수 있다 (회원가입용 스키마+API+UI)
작업 2: 사용자가 로그인할 수 있다 (인증 스키마+API+UI)
작업 3: 사용자가 작업(task)을 생성할 수 있다 (task 스키마+API+UI)
작업 4: 사용자가 작업 목록을 볼 수 있다 (조회+API+목록 UI)
```

각 수직 슬라이스는 그 자체로 동작하고 테스트 가능한 기능을 제공한다.

### 4단계: 작업 작성하기

각 작업은 다음 구조를 따른다:

```markdown
## 작업 [N]: [간단한 제목]

**설명:** 이 작업이 무엇을 달성하는지 한 문단으로 설명.

**수용 기준(acceptance criteria):**
- [ ] [구체적이고 테스트 가능한 조건]
- [ ] [구체적이고 테스트 가능한 조건]

**검증:**
- [ ] 테스트 통과: [해당 저장소의 관련 테스트 실행 명령]
- [ ] 빌드 성공: [해당 저장소의 빌드 명령]
- [ ] 수동 확인: [확인할 내용 설명]

**의존성:** [이 작업이 의존하는 작업 번호, 없으면 "없음"]

**영향받는 파일(예상):**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**예상 규모:** [소: 파일 1~2개 | 중: 파일 3~5개 | 대: 파일 5개 이상]
```

### 5단계: 순서 정하기와 체크포인트 배치

작업을 다음과 같이 배치한다:

1. 의존성이 충족되도록 (기반부터 먼저 구축)
2. 각 작업이 끝난 뒤에도 시스템이 동작하는 상태를 유지하도록
3. 2~3개 작업마다 검증 체크포인트가 오도록
4. 위험도가 높은 작업은 앞쪽에 배치 (빠르게 실패하기 위해)

명시적인 체크포인트를 추가한다:

```markdown
## 체크포인트: 작업 1~3 완료 후
- [ ] 모든 테스트 통과
- [ ] 애플리케이션이 에러 없이 빌드됨
- [ ] 핵심 사용자 흐름이 처음부터 끝까지 동작함
- [ ] 다음 단계 진행 전 사람의 검토를 받음
```

## 작업 규모 산정 기준

| 규모 | 파일 수 | 범위 | 예시 |
|------|-------|------|------|
| **XS** | 1개 | 함수 하나 또는 설정 변경 | 검증 규칙 하나 추가 |
| **S** | 1~2개 | 컴포넌트 또는 엔드포인트 하나 | 새 API 엔드포인트 추가 |
| **M** | 3~5개 | 기능 슬라이스 하나 | 사용자 회원가입 흐름 |
| **L** | 5~8개 | 여러 컴포넌트가 걸친 기능 | 필터링·페이지네이션이 있는 검색 |
| **XL** | 8개 이상 | **너무 큼 — 반드시 더 쪼갤 것** | — |

작업이 L 이상이면 더 작은 작업으로 쪼개야 한다. 에이전트는 S와 M 크기의 작업에서 가장 좋은 성능을 낸다.

**다음 경우 작업을 더 쪼개야 한다:**
- 한 번의 집중 세션(대략 에이전트 작업 시간 2시간 이상)을 초과할 것 같을 때
- 수용 기준을 3개 이하의 항목으로 설명할 수 없을 때
- 서로 독립된 두 개 이상의 하위 시스템에 걸쳐 있을 때 (예: 인증과 결제)
- 작업 제목에 "그리고(and)"가 들어간다는 것을 발견했을 때 (사실은 두 작업이라는 신호)

## 결과물 파일

- **계획 문서:** 구현 계획을 `tasks/plan.md`에 저장한다.
- **작업 목록:** 체크리스트 형태의 작업 목록을 `tasks/todo.md`에 저장한다.

`tasks/` 디렉토리가 없으면 새로 만든다. 이 경로들은 `/build` 명령 등 후속 도구가 기대하는 관례(convention)다.

## 계획 문서 템플릿

```markdown
# 구현 계획: [기능/프로젝트 이름]

## 개요
[무엇을 만드는지 한 문단 요약]

## 아키텍처 결정 사항
- [핵심 결정 1과 그 근거]
- [핵심 결정 2와 그 근거]

## 작업 목록

### 1단계: 기반 구축
- [ ] 작업 1: ...
- [ ] 작업 2: ...

### 체크포인트: 기반 구축 완료
- [ ] 테스트 통과, 빌드 정상

### 2단계: 핵심 기능
- [ ] 작업 3: ...
- [ ] 작업 4: ...

### 체크포인트: 핵심 기능 완료
- [ ] 처음부터 끝까지 흐름이 동작함

### 3단계: 다듬기
- [ ] 작업 5: ...
- [ ] 작업 6: ...

### 체크포인트: 완료
- [ ] 모든 수용 기준 충족
- [ ] 검토 준비 완료

## 위험 요소와 대응 방안
| 위험 | 영향도 | 대응 전략 |
|------|--------|------------|
| [위험 요소] | [높음/중간/낮음] | [전략] |

## 열린 질문
- [사람의 판단이 필요한 질문]
```

## 병렬화 가능 지점

여러 에이전트나 세션을 동시에 쓸 수 있을 때:

- **병렬화해도 안전한 것:** 서로 독립적인 기능 슬라이스, 이미 구현된 기능에 대한 테스트, 문서 작업
- **반드시 순차적이어야 하는 것:** 데이터베이스 마이그레이션, 공유 상태 변경, 의존성 체인
- **조율이 필요한 것:** API 계약을 공유하는 기능들 (계약을 먼저 정의한 뒤 병렬화)

## 흔한 자기합리화

| 자기합리화 | 실제 현실 |
|---|---|
| "하면서 알아가면 되지" | 그렇게 하면 뒤엉킨 결과물과 재작업으로 끝난다. 10분의 계획이 몇 시간을 절약한다. |
| "작업이 뻔히 보이는데" | 그래도 적어라. 명시적으로 작업을 적으면 숨어있던 의존성과 잊고 있던 예외 상황이 드러난다. |
| "계획은 오버헤드다" | 계획 자체가 작업이다. 계획 없는 구현은 그냥 타이핑일 뿐이다. |
| "머릿속에 다 담아둘 수 있어" | 컨텍스트 윈도우는 유한하다. 글로 적어둔 계획만이 세션 경계와 컨텍스트 압축을 넘어 살아남는다. |

## 위험 신호(Red Flags)

- 작성된 작업 목록 없이 바로 구현을 시작함
- 수용 기준 없이 "그 기능을 구현하라"라고만 적힌 작업
- 계획에 검증 단계가 없음
- 모든 작업이 XL 크기임
- 작업 사이에 체크포인트가 없음
- 의존성 순서를 고려하지 않음

## 검증

구현을 시작하기 전에 다음을 확인한다:

- [ ] 모든 작업에 수용 기준이 있는가
- [ ] 모든 작업에 검증 단계가 있는가
- [ ] 작업 간 의존성이 파악되고 올바른 순서로 정렬되어 있는가
- [ ] 어떤 작업도 대략 5개 이상의 파일을 건드리지 않는가
- [ ] 주요 단계 사이에 체크포인트가 있는가
- [ ] 사람이 계획을 검토하고 승인했는가

## 참고

수용 기준(acceptance criteria)은 작업 단위별로 "우리가 맞는 것을 만들었는가?"에 답한다. 이는 프로젝트 전체에 적용되는 "완료의 정의(Definition of Done)" — 모든 작업이 완료로 인정받기 전에 통과해야 하는 공통 기준 — 위에 놓인다. `references/definition-of-done.md`를 참고할 것.
