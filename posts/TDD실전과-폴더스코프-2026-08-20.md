# 스킬·슬래시 명령도 폴더에 묶인다 — Excel 메뉴판으로 배우는 TDD 실전

지난 글에서 `/resume`이 실행한 폴더 기준이라는 걸 확인했는데, 오늘은 그 원리가 스킬(Skill)과 슬래시 명령에도 똑같이 적용된다는 걸 실전 프로젝트를 진행하며 직접 겪었다. 동시에 새 프로젝트(카페 메뉴판, Excel+SSE 연동)를 Kent Beck의 TDD Red-Green-Refactor·Tidy First 방식으로 처음부터 끝까지 진행하며 그 절차를 손으로 익혔다.

## 스킬과 슬래시 명령도 폴더에 묶인다

한 세션에서 서로 다른 두 프로젝트(`menupan`, `my-blog`)의 스킬을 같이 쓸 수 있는지 물어보며 시작했는데, 확인해보니 안 됐다. 이유는 스킬·슬래시 명령이 **프로젝트 디렉터리 기준으로 스코프**되기 때문이다.

재미있는 건 이 둘의 동작 방식이 살짝 다르다는 점이다.

- **스킬(`.claude/skills/`)**: 세션 도중 그 폴더 안 파일을 실제로 읽으면 그 자리에서 동적으로 "새 스킬 발견됨" 하고 등록된다.
- **슬래시 명령(`.claude/commands/`)**: 세션이 **시작된 시점**의 디렉터리 기준으로 한 번만 스캔된다. 세션 도중 새로 만든 명령 파일은 그 세션에서 끝까 안 잡힌다.

실제로 겪은 순서: 새 프로젝트 폴더(`menupan`) 안에 슬래시 명령(`/tdd-red` 등)을 만들었는데 인식이 안 됐다 → 세션을 새로 열면 되겠지 생각했는데, 그 폴더에서 새로 열면 **이번엔 세션 이력(`--resume`)이 안 이어졌다** — 세션 기록도 시작 디렉터리별로 따로 저장되는 거였다. 결국 하나의 원리(프로젝트=폴더 스코프)가 스킬·명령·세션 이력 세 군데 모두에 적용된다는 걸 세 번 연달아 확인한 셈이다.

해결은 `handoff` 스킬로 `.handoff.md`에 진행 상태를 남기는 것 — 대화 기록이 안 넘어가도 프로젝트 파일(`CLAUDE.md`, `plan.md` 등)에 상태가 다 적혀 있으면 새 세션이 그걸 읽고 이어갈 수 있다.

## Excel 메뉴판으로 TDD Red-Green-Refactor 실전

카페 메뉴판(Excel 파일 하나로 화면을 구동, 저장하면 SSE로 자동 갱신되는 프로젝트)의 `PRD.md`/`TRD.md`를 작성하고, `CLAUDE.md`에 Kent Beck의 TDD 지침을 그대로 심어서(원문 인용) 개발 프로세스로 강제했다. 이후 `plan.md`에 작은 단위 테스트 체크리스트를 만들고 하나씩 Red→Green→Refactor로 실제 구현했다.

실전에서 겪은 핵심 포인트:

| 단계 | 실제로 한 일 |
|---|---|
| Red | `test/menu-parser.test.mjs`에 `parseMenuSheet(sheetRows)`가 특정 입력에 특정 출력을 내야 한다는 테스트를 먼저 작성 — 구현 파일이 없어 `ERR_MODULE_NOT_FOUND`로 실패하는 걸 직접 확인 |
| Green | 그 테스트 하나만 통과시키는 최소 코드 작성(가짜 구현도 허용) |
| Refactor | 통과 상태를 유지하며 구조만 정리, 필요 없으면 "필요 없음"이라고 명시 |

가장 인상 깊었던 건 **품절 판정 로직을 구현하면서 이미 Green이던 첫 테스트의 기대값을 다시 고쳐야 했던 순간**이다. `품절` 문자열 필드를 `soldOut` 불리언으로 바꾸기로 결정하면서, 이미 통과하던 테스트의 기대 객체 모양도 같이 바뀌어야 했다 — 의도적으로 기존 테스트를 다시 Red로 만든 뒤 구현을 갱신한 케이스였다. 버그 수정(새 테스트 추가)과 사양 변경(기존 테스트 수정)은 다른 절차라는 걸 실감했다.

## Tidy First — 구조적 변경과 행위적 변경은 절대 안 섞는다

- **구조적 변경**: 행위는 그대로 두고 이름 바꾸기·함수 추출 같은 재배치.
- **행위적 변경**: 실제 동작·결과가 바뀌는 것.

한 커밋에 이 둘을 섞으면 나중에 테스트가 깨졌을 때 리팩터 때문인지 기능 변경 때문인지 구분이 안 된다. 그래서 둘 다 필요하면 구조적 변경 → 테스트 확인 → 커밋, 그다음 행위적 변경 → 테스트 확인 → 커밋 순으로 반드시 분리한다.

## 그 밖에 짚은 개념들

| 개념 | 핵심 |
|---|---|
| npm의 `package.json` 탐색 | git이 `.git` 찾듯, cwd에 없으면 상위 폴더로 계속 올라가며 찾는다(가장 가까운 것 하나만 사용) |
| `server.mjs` / `chokidar` / `SheetJS` | 각각 "서버 진입점 파일", "파일 변경 감시 라이브러리", "Excel↔JSON 변환 라이브러리" |
| SSE vs WebSocket | SSE는 서버→클라이언트 단방향, 순수 HTTP 위에서 동작, 자동 재연결 내장. 양방향이 필요 없는 읽기 전용 화면엔 SSE로 충분 |

## rewind보다 타겟 Edit

작업 중 실수(엉뚱한 방향으로 파일을 고친 상황)를 되돌릴 때 `rewind`가 항상 정답은 아니었다. rewind는 그 시점 이후 모든 작업을 통째로 되돌리기 때문에, 그 사이에 만든 다른 좋은 결과물까지 같이 날아간다. 특정 파일 하나만 원래 내용으로 되돌리면 되는 상황이면, 이미 대화 맥락에 있는 원본 내용으로 그 파일만 Edit하는 게 훨씬 안전하고 저렴했다.

## 실습하며 나온 질문들

***Q). menupan 스킬이랑 my-blog 스킬을 한 세션에서 같이 쓸 수 있어?***  
A). 안 된다. 둘 다 프로젝트 디렉터리 기준으로 스코프되기 때문에, 지금 세션의 스코프 밖 프로젝트 스킬은 안 보인다. 각 프로젝트 폴더에서 별도 세션을 열어야 한다.

***Q). npm install이 지금 작성한 package.json을 참고하라는 게 어디 명시돼있어? 다른 프로젝트에 package.json이 있어도 상관없어?***  
A). 어떤 설정이 그렇게 정한 게 아니라 npm 프로그램 자체에 하드코딩된 규칙이다. cwd에 없으면 상위로 한 칸씩 올라가며 찾고, 제일 가까운 것 하나만 쓴다. 실제로 하위 폴더에서 실행해도 상위 package.json을 찾아 쓰는 걸 확인했다.

***Q). server.mjs, chokidar, SheetJS 각각 뭐야?***  
A). server.mjs는 서버 진입점 파일(ESM 확장자), chokidar는 파일 변경 감시 라이브러리, SheetJS(xlsx)는 Excel 파일을 JSON으로 변환하는 라이브러리다. 이 프로젝트에선 chokidar가 저장 감지 → SheetJS가 파싱 → server.mjs(express)가 SSE로 푸시하는 흐름으로 엮인다.

***Q). SSE 방식이 WebSocket이랑 어떻게 달라?***  
A). SSE는 서버→클라이언트 단방향만, 순수 HTTP 위에서 동작하고 브라우저가 자동 재연결해준다. WebSocket은 양방향에 별도 프로토콜 핸드셰이크가 필요하다. 읽기 전용 화면(메뉴판)엔 양방향이 필요 없어 SSE로 충분하다.

***Q). "테스트 먼저 작성한다"는 게 코드를 쓰는 거야, 시나리오를 쓰는 거야?***  
A). 실행되는 진짜 코드다. `assert.deepEqual` 같은 걸로 실제로 실행 가능한 검증 코드를 먼저 만들고, 그게 실패하는 걸 실제로 확인한 다음 구현에 들어간다.

***Q). 예상 가능한 모든 예외 케이스를 미리 다 테스트에 넣어야 하는 거야?***  
A). 아니다. 지금 확실히 정의된 스펙만 먼저 넣고, 구현하다 실제로 마주치는 애매한 케이스는 그때 기대 동작부터 정하고 테스트를 추가한다. "이 입력을 넣으면 지금 코드가 틀린 답을 낸다"고 말할 수 없는 케이스는 아직 필요 없는 테스트다.

***Q). Tidy First에 대해서 더 자세히 설명해줘.***  
A). 구조적 변경(행위 안 바뀜)과 행위적 변경(기능이 바뀜)을 절대 한 커밋에 섞지 않는 원칙이다. 섞으면 테스트가 깨졌을 때 원인 추적이 안 되고, 리뷰어도 의도된 변경인지 실수인지 구분 못 한다. 둘 다 필요하면 구조적 변경을 먼저 끝내고 검증한 뒤 행위적 변경으로 넘어간다.

***Q). rewind로 되돌리는 게 나을까?***  
A). 파일 하나의 특정 부분만 되돌리면 되는 상황이면 rewind보다 타겟 Edit이 낫다. rewind는 그 시점 이후 모든 작업을 통째로 되돌리기 때문에, 사이에 만든 다른 결과물까지 같이 날아간다.

***Q). 새 프로젝트 폴더에서 세션을 새로 열었는데 왜 이 대화를 못 불러와?***  
A). 세션 이력도 스킬·명령과 같은 원리로 **세션이 시작된 정확한 디렉터리** 기준으로 저장된다. 다른 폴더에서 시작한 세션의 이력은 `--resume`으로도 안 이어진다. 대신 `.handoff.md`나 프로젝트 문서(`plan.md` 등)에 상태를 남겨두면 새 세션이 그걸 읽고 이어갈 수 있다.

## 마무리

프로젝트=폴더 스코프 원리가 세션 이력뿐 아니라 스킬·슬래시 명령까지 일관되게 적용된다는 걸 실제로 막혀보면서 확인했다. 그리고 Kent Beck TDD를 문서로만 알던 것과 실제로 Red 상태를 눈으로 보고 최소 구현으로 Green을 만들어보는 건 확실히 다른 감각이었다.
