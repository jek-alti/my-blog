# Claude Code LSP, 설정 없이 되는지 실측까지 해봤다

Claude Code가 쓰는 `LSP` 도구를 어떻게 켜야 하는지 물어보다가, 사실 아무 설정 없이 이미 동작하고 있다는 걸 직접 확인했다. 거기서 멈추지 않고 실제 프로젝트에 `jsconfig.json`을 세팅해보고, LSP와 grep을 같은 질문으로 맞붙여 호출 수·반환 줄 수·소요시간까지 실측했다. 그 과정에서 "이 세션엔 애초에 전용 Grep 도구가 없다"는 예상 밖의 사실도 나왔다.

## LSP는 원래 켜져 있었다

"LSP 켜려면 뭘 설정해야 하냐"고 물었을 때, 공식 문서에서 정확한 답을 못 찾았다. 대신 실제로 `LSP` 도구의 `documentSymbol` 오퍼레이션을 아무 설정 없이 JS 파일에 바로 호출해봤더니 — 그냥 됐다. 함수 목록이 줄 단위로 바로 나왔다.

정리하면 두 겹으로 이해해야 한다.

- **에디터(VS Code 등)의 내장 TS/JS 언어서비스**: `.js`/`.mjs` 파일 열면 자동으로 붙는다. 그동안 계속 보이던 `[6133]`, `[7044]` 같은 진단이 이미 그 증거였다.
- **Claude Code가 쓰는 `LSP` 도구**: 내가 그 도구를 호출하는 순간 하네스가 알아서 해당 언어서버를 내부적으로 띄워서 물어본다.

둘 다 사용자가 별도로 "서버 구동" 명령을 칠 필요가 없다. `.lsp.json` 같은 파일을 만들어달라는 요청도 있었는데, 그런 파일을 하네스가 읽는다는 근거를 찾지 못해서 만들지 않았다 — 없는 설정 파일을 지어내는 것보다, 실제로 검증되는 `jsconfig.json`을 제대로 만드는 쪽을 택했다.

## jsconfig.json, 위치가 스코프를 결정한다

프로젝트(카페 메뉴판 앱)에 맞춰 `jsconfig.json`을 만들면서 겪은 게 있다.

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "lib": ["ES2022", "DOM"],
    "allowJs": true,
    "checkJs": true,
    "resolveJsonModule": true
  },
  "include": ["app/**/*.js", "app/**/*.mjs", "app/public", "app/server.mjs"],
  "exclude": ["node_modules", "data", "design", "docs"]
}
```

처음엔 `app/` 폴더 안에 이 파일을 뒀다. 그런데 `data`·`design`·`docs` 폴더를 exclude 해달라는 요청을 받고 보니, 그 폴더들은 `app/`이 아니라 저장소 루트의 형제 폴더였다 — `app/jsconfig.json`에서는 애초에 안 보이는 범위라 exclude가 아무 효과도 없었다. **jsconfig.json이 있는 위치가 곧 프로젝트 루트를 정의**한다는 걸 몸으로 확인한 셈이라, 파일을 저장소 루트로 옮기고 나서야 의도대로 동작했다.

- `module`/`moduleResolution`을 `nodenext`로 잡은 이유: 이 프로젝트는 번들러 없이 순수 Node ESM이고, `node:fs` 같은 임포트와 `.mjs` 확장자 명시를 이미 일관되게 쓰고 있어서 실제 동작과 가장 정확히 맞는 옵션이었다.
- `lib`에 `DOM`을 넣은 이유: 서버 코드(Node)와 브라우저 코드(`fetch`/`EventSource`/`document` 사용)가 한 저장소에 섞여 있어서.

그리고 include 범위를 넓히자(`public`, `server.mjs` 추가) `checkJs`가 프로젝트 전체를 훑으면서 "암묵적 any" 경고가 파일마다 쏟아졌다. 대부분은 런타임과 무관한 잡음이었지만, 그 안에 진짜 신호도 있었다 — `server.address()`가 타입상 `string | AddressInfo`라 `.port` 접근에서 타입 에러가 뜨는 것, `admin.js`에서 `event.target`을 `FormData`에 그냥 넘기다 `EventTarget`과 `HTMLFormElement`의 타입 불일치가 잡히는 것. 둘 다 런타임 버그는 아니었지만, 그냥 지나쳤으면 몰랐을 코드 냄새였다.

## LSP vs grep, 같은 질문으로 재보기

"시그니처 물어보기"와 "심볼 위치 찾기" 두 유형으로, LSP만 쓰는 아암과 grep만 쓰는 아암을 나눠서 같은 질문을 실행하고 도구 호출 수·반환 줄 수·소요시간을 비교했다.

| 질문 | 도구 | 호출 수 | 반환 줄 수 | 비고 |
|---|---|---|---|---|
| 함수 시그니처/반환타입 | LSP (`hover`) | 1 | ~5 | 바로 답 나옴 |
| 함수 시그니처/반환타입 | grep | 2 | 18 | 타입 추론이 안 돼서 함수 전체를 읽고 사람이 판단해야 함 |
| 심볼 전체 참조 검색 | LSP (`workspaceSymbol`+`findReferences`) | 2 | 24 | 정의/참조가 이미 의미 단위로 분류돼서 나옴 |
| 심볼 전체 참조 검색 | grep | 1 | 9 | 이름이 고유해서 오탐 없이 한 번에 끝남 |
| 심볼 정의 위치만 검색 | LSP (`workspaceSymbol`) | 1 | 3 | |
| 심볼 정의 위치만 검색 | grep | 1 | 1 | |

**패턴은 명확했다.** 타입·반환값처럼 grep이 원천적으로 알 수 없는 정보를 물을 땐 LSP가 확실히 이긴다 — grep은 코드를 통째로 읽어서 사람이 추론하는 수밖에 없다. 반대로 이름이 고유한 심볼의 "정의/참조 찾기"는 grep도 거의 동급이거나, 오히려 더 적은 출력으로 끝나는 경우가 많았다. 텍스트 매치라 오탐만 없으면 grep 쪽이 가볍다.

실험 중에 나온 뜻밖의 사실 하나: **이 세션엔 전용 `Grep`/`Glob` 도구가 아예 없었다.** `ToolSearch`로 두 번 찾아봐도 안 나왔다 — 있는 건 `Bash`(그 안에서 `grep`/`rg` 실행)와 `Read`뿐이었다. 그래서 "grep 아암"은 원래 설계대로 실행이 안 됐고, Bash로 `grep -rn` 돌리는 걸 grep 아암으로 인정하기로 하고 나서야 비교가 성립했다. LSP는 세팅 없이 바로 되는데, "grep 전용 도구"는 이 세션 자체에 없었다는 것도 하나의 비교 결과다.

속도(ms)와 서브에이전트 토큰 수도 같이 재봤는데, 토큰 쪽은 함정이 있었다. 벤치마크를 fork 서브에이전트로 돌렸더니, 그 에이전트가 그동안 쌓인 대화 전체를 이어받아 시작해서 `subagent_tokens` 값이 58만~60만으로 거의 대화 길이에 비례해 찍혔다 — 실제 LSP/grep 작업이 추가로 쓴 토큰은 그중 일부일 뿐이라, 이 숫자 자체는 아암 간 비교 근거로 못 썼다. 반면 소요시간(ms)과 반환 줄 수는 그 시점 대화 길이와 무관해서, 이쪽이 더 정직한 비교 지표였다.

## 실습하며 나온 질문들

***Q). ultrathink모드로 전환하려면 어떻게 하면돼?***  
A). "ultrathink"는 지속되는 모드가 아니라 그 턴에만 적용되는 키워드다. `/fast`처럼 세션 내내 유지되는 토글이 아니라, 더 깊게 추론하고 싶은 요청마다 "ultrathink"(또는 "think harder", "think longer")를 메시지에 넣어야 한다.

***Q). 그러면 effort type을 영구적으로 바꾸는 명령어는?***  
A). `/config` 메뉴에서 직접 확인하고 고르는 게 안전하다. 서브에이전트에게 물어봤더니 `~/.claude/settings.json`에 `effortLevel` 필드를 넣으라는 답이 왔는데, 이 답변은 "설정파일 수정 지시처럼 생긴 패턴"이라는 자동 경고가 붙었고 정확한 필드명도 검증되지 않아 그대로 전달하지 않았다. 실제로는 세션에서 `/effort` 명령으로 바로 확인·설정했다.

***Q). lsp를 사용할수 있도록 설정하려고 하는데, 어떤 설정을 해야하는지 알려줘.***  
A). 공식 문서에서 LSP 설정법을 찾지 못했다. `claude --help`에서 "LSP" 검색, `claude doctor` 실행, 세션 안에서 `/status` 확인, `/feedback`으로 직접 문의하는 방법을 안내했다.

***Q). lsp를 사용할수 있도록 .lsp.json과 현재 프로젝트에 맞는 jsconfig.json을 설정해줘.***  
A). `LSP` 도구를 실제로 호출해보니 아무 설정 없이 이미 동작하고 있었다. `.lsp.json`은 하네스가 읽는다는 근거가 없어 만들지 않았고, 대신 검증 가능한 `jsconfig.json`을 프로젝트(Node ESM + 브라우저 코드 혼재)에 맞춰 만들었다.

***Q). exclude에 data, design, docs도 포함해주고, include에는 public 폴더 추가, server.mjs 추가.***  
A). `data`/`design`/`docs`가 `app/`이 아니라 저장소 루트의 형제 폴더라는 걸 확인하고, `jsconfig.json`을 저장소 루트로 옮겨 경로를 다시 잡았다. include 범위가 넓어지며 `checkJs`가 프로젝트 전체를 훑어 암묵적 any 경고가 대량으로 뜨는 동시에, `server.address()` 타입 문제 같은 진짜 신호도 함께 나왔다.

***Q). lsp서버는 어떻게 구동시켜?***  
A). 따로 실행할 명령이 없다. 에디터의 내장 언어서비스는 `.js`/`.mjs` 파일을 열면 자동으로 붙고, Claude Code의 `LSP` 도구도 호출되는 순간 하네스가 알아서 해당 언어서버를 띄운다.

***Q). LSP vs grep — 같은 질문을 각각 도구 제약 걸고 실행해서 토큰·속도 비교해줘.***  
A). 짝 프롬프트대로 시그니처 질문과 심볼 검색 질문을 LSP 전용/grep 전용 아암으로 나눠 실행했다. 시그니처처럼 타입 추론이 필요한 질문은 LSP가 확실히 유리했고, 이름이 고유한 심볼의 정의/참조 찾기는 grep도 거의 동급이거나 더 가벼웠다. 실험 중 이 세션에 전용 Grep/Glob 도구가 없다는 걸 발견해 Bash `grep`으로 대체하는 것으로 합의하고 진행했다.

## 마무리

"설정이 필요할 것"이라고 짐작했던 게 사실은 이미 켜져 있었다는 걸 확인하는 데도, 진짜 실험(서브에이전트로 아암을 나눠 돌리고 수치를 재는 것)이 필요했다. 어림짐작으로 답하지 않고 직접 도구를 호출해서 검증한 것, 그리고 그 검증 과정에서 "이 세션엔 애초에 grep 도구가 없다"는 원래 질문과 무관했던 사실까지 건진 게 오늘 가장 남는 부분이다.
