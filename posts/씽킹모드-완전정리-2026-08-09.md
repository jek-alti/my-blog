# 클로드 코드 Thinking Mode와 Effort 완전 정리

오늘은 클로드 코드의 편집모드와 모델 설정부터 시작해서, thinking mode와 adaptive thinking의 관계를 아주 깊게 파고들었다. 특히 "thinking을 끈다"는 게 정확히 무엇을 의미하는지, effort와는 어떻게 다른지, 그리고 content block 구조와 비용 구조까지 공식 문서 레벨로 하나씩 확인하며 정리했다. 중간에 스스로도 헷갈려서 몇 번씩 되짚어봤는데, 그 과정을 그대로 남겨둔다.

## 기본 설정들

### 편집모드 전환

클로드 코드의 편집모드(permission mode)는 `Shift + Tab`으로 전환한다. plan / default / acceptEdits / auto / dontAsk 등 에이전트가 작업을 진행할 때 사용자에게 얼마나 확인을 받을지의 수준을 정하는 설정이다.

### 모델별 컨텍스트 윈도우

Opus/Sonnet 4.6 기준으로 기본 200K 토큰(약 500페이지 분량 텍스트), 확장하면 1M 토큰(약 2500페이지 분량)까지 지원한다.

### 모델 변경 방법 4가지 (우선순위 순)

우선순위: **세션 중 명령어 > 시작 플래그 > 환경변수 > 설정파일**. 그래서 환경변수로 기본값을 정해두고, 필요할 때만 세션 중 명령어로 일시 전환하는 방식이 효율적이다.

| 순위 | 방법 | 예시 |
|---|---|---|
| 1 | 세션 중 명령어 | `/model sonnet` 또는 `/config model=sonnet` — 지금 켜져 있는 세션에서 즉시 바뀜 |
| 2 | 시작 플래그 | `claude --model sonnet` — 터미널에서 `claude` 실행할 때 지정 |
| 3 | 환경변수 | `~/.zshrc` 또는 `~/.bashrc`에 `export ANTHROPIC_MODEL="claude-sonnet-5"` 추가 후 새 터미널에서 `claude` 실행 시 적용 |
| 4 | 설정파일 | `~/.claude/settings.json`에 `"model": "sonnet"` 항목 추가 |

우선순위가 위와 같으므로, 예를 들어 환경변수로 `claude-sonnet-5`를 기본값으로 깔아둔 상태에서 특정 세션에서만 `/model opus`로 바꾸면 그 세션 동안은 opus가 우선 적용된다.

실습하며 직접 확인한 것: 환경변수는 **프로세스가 시작될 때** 딱 한 번 읽히는 값이다. 이미 실행 중인 세션에서 `.zshrc`를 수정해도 그 세션에는 반영되지 않고, `source ~/.zshrc`를 해도 마찬가지다 (Bash 도구가 실행하는 셸 자체가 매번 초기화되는 별도 서브프로세스이기도 하고, 애초에 이미 떠 있는 `claude` 프로세스는 그 값을 다시 읽지 않기 때문이다). 새 터미널을 열어서 `claude`를 재시작해야 반영된다.

## Thinking Mode와 Adaptive Thinking — 최종 정리

이 부분이 오늘의 핵심이다. 처음엔 "thinking mode = 화면에 사고 과정을 보여줄지 말지 정하는 스위치"라고 이해했는데, 여러 번 되짚어보니 그게 전부가 아니었다.

### 기본 개념

- **Adaptive thinking**은 모델(Sonnet 5, Opus 5, Fable 5 등)이 요청마다 추론이 얼마나 필요한지 스스로 판단해서 토큰을 알아서 할당하는 메커니즘이다. 구형 모델들이 쓰던 `budget_tokens`(고정 토큰 상한을 미리 지정하는 방식)를 대체한다.
- Sonnet 5, Opus 5는 adaptive thinking이 **기본값으로 켜져 있다.** 반면 Opus 4.8/4.7/4.6, Sonnet 4.6은 기본값이 꺼짐이라 명시적으로 켜야 한다.
- **Extended thinking(레거시)**과 **adaptive thinking(신형)**은 서로 다른 메커니즘이지만, 둘 다 결과적으로 `thinking`이라는 content block을 만들어낸다는 공통점이 있다.

### thinking=true/false는 정확히 무엇을 켜고 끄는가

이 질문에 대한 답이 대화 내내 계속 정교해졌다. 최종적으로 확인된 사실은:

- Claude Code의 `/config thinking=true|false`는 **단순히 화면 표시(display)만 조절하는 스위치가 아니다.** 실제로 adaptive thinking의 **추론 단계 자체를 켜고 끈다** — API 파라미터로 치면 `thinking.type`을 `"adaptive"` ↔ `"disabled"`로 바꾸는 것과 동일한 효과다.
- 화면 표시만 따로 조절하는 옵션은 별도로 `display` 필드(`"summarized"` vs `"omitted"`)이며, 이건 `type`과는 완전히 다른 차원의 설정이다. `type`은 "추론을 하느냐 마느냐", `display`는 "이미 하고 있는 추론을 보여주느냐 마느냐"를 결정한다.
- 이 구분이 헷갈렸던 이유는, `/config thinking=false`가 두 가지 효과(추론 안 함 + 당연히 화면에도 안 보임)를 동시에 내기 때문이다. 화면에 안 보이는 이유가 "숨겨서"가 아니라 "애초에 발생을 안 시켜서"라는 게 핵심이다.
- 이건 Anthropic API를 직접 쓰는 환경(예: Claude Pro/Max 구독이나 Console API 키로 Claude Code를 쓰는 경우)에서 그렇다는 것도 확인했다. Amazon Bedrock, Google Vertex AI, Microsoft Foundry 같은 서드파티 프로바이더를 거치는 환경에서는 파라미터가 생략될 뿐이라 adaptive-reasoning 모델이 여전히 내부적으로 추론할 수도 있다는 차이가 있다. 지금 쓰는 환경(VSCode 확장, `CLAUDE_CODE_USE_BEDROCK`/`CLAUDE_CODE_USE_VERTEX` 환경변수 없음)은 Anthropic API 직접 사용 환경이라 이 설명이 그대로 적용된다.
- **adaptive thinking이 없는 구형 모델(Haiku 4.5, Opus/Sonnet 4.5 이하)에서도 `/config thinking=true`는 똑같이 작동한다.** Claude Code가 해당 모델이 지원하는 방식(adaptive가 있으면 adaptive, 없으면 legacy extended thinking)을 자동으로 골라서 켠다. 즉 "adaptive thinking이 켜져 있어야만 thinking 표시가 된다"는 전제는 틀렸다 — 두 메커니즘 모두 결과적으로 `thinking` content block을 만들고, `display`라는 표시 레이어는 그 위에서 공통으로 작동한다.

### "추론 단계를 생략한다"는 것의 구체적인 의미

여기서부터는 모델이 텍스트를 만드는 방식과 연결해서 이해해야 한다.

모델은 토큰을 하나씩 순서대로 만들어낸다(autoregressive). 토큰 하나를 만들고 → 그걸 다시 입력에 포함시켜서 다음 토큰을 만들고 → 이걸 반복한다. 그래서 "토큰을 몇 개 만드느냐"가 곧 "얼마나 많은 계산 단계를 거치느냐"와 직결된다.

**thinking이 켜져 있을 때**는 실제로 두 단계를 거친다.
1. **추론 단계**: `thinking` block 안에 토큰들을 순서대로 실제로 생성한다. "이 문제는 A와 B를 비교해야 하고..." 같은 중간 과정을 진짜로 토큰 단위로 만들어내는, 시간과 비용이 드는 진짜 작업이다.
2. **답변 단계**: 1단계의 추론 내용을 참고해서 `text` block에 최종 답변 토큰을 생성한다.

**thinking이 꺼져 있을 때**는 1단계가 통째로 없다. "추론은 하되 안 보여주는 것"이 아니라, 애초에 추론 토큰을 만드는 그 생성 루프 자체를 실행하지 않는 것이다. 그래서 만들어지는 토큰 수가 줄고, 지연시간이 짧아지고, 과금되는 토큰도 적어진다. 다만 복잡한 문제에서는 "미리 풀어보는 과정" 없이 바로 답을 내놓는 셈이라 정확도가 떨어질 위험이 있다.

비유하자면, thinking 켜짐은 "연습장에 풀이 과정을 실제로 적어본 다음 답을 쓰는 것"이고, thinking 꺼짐은 "연습장 없이 머릿속에서 바로 답을 말하는 것"이다. 연습장을 숨기는 게 아니라 애초에 연습장을 안 쓰는 것이라는 비유가 이 개념을 가장 잘 설명해준다.

한 가지 덧붙이면, "완전히 끄면 아무 연산도 없이 반사적으로 답하느냐"는 질문에는 조심할 필요가 있다. thinking 토큰(=명시적으로 눈에 보이는 단계적 사고)이 없다는 것과, 트랜스포머가 최종 답변 토큰 하나하나를 만들 때도 신경망 연산(forward pass)을 거친다는 것은 서로 다른 층위의 이야기다. 후자는 thinking on/off와 무관하게 항상 일어나는, 모델 구조상 당연한 계산이다. 다만 이건 Anthropic 공식 문서로 확인된 내용이 아니라 트랜스포머 구조 일반론으로 보충한 설명이라는 점은 구분해둔다.

### Adaptive thinking을 끌 수 있는가

- **만능설정 맞다**: adaptive thinking은 추론 깊이와 토큰 예산을 둘 다 자동으로 조절한다. Fable 5, Sonnet 5, Opus 4.7 이후 모델은 항상 adaptive reasoning을 쓴다.
- **끄는 것은 가능하지만 모델별 제약이 있다.** API 레벨에서 `thinking: {type: "disabled"}`로 설정하면 정말로 끌 수 있다 — 단, Fable 5는 아예 끌 수 없고(`thinking cannot be turned off`), Opus 5는 effort가 `high` 이하일 때만 끌 수 있고 `xhigh`/`max`와는 같이 못 쓴다(400 에러).

## Effort와 Adaptive Thinking의 관계

- `effort`(low/medium/high/xhigh/max)는 추론 깊이를 조절하는 "부드러운 지침(soft guidance)"이지, 정확한 토큰 상한을 보장하는 값은 아니다.
- 매 질문마다 effort를 수동으로 바꿀 필요는 없다. adaptive thinking이 이미 요청 난이도에 따라 자동으로 조절해주기 때문이다. 오히려 effort 값을 바꾸면 prompt cache가 무효화되기 때문에, 질문마다 effort를 이리저리 바꾸는 건 캐시 손해까지 더해져 오히려 비효율적이다. 대신 effort는 세션에서 적절한 기본값으로 한 번 정해두고, 특정 질문에 더 깊거나 얕은 추론을 유도하고 싶으면 프롬프트에 직접 지침을 넣는 방식(per-message steering)을 쓰는 게 낫다 — 예를 들어 "고민하지 말고 바로 답해줘" 또는 "충분히 고민한 후 답해줘" 같은 문장을 추가하는 식이다.
- **단, Sonnet 5는 effort 수준을 엄격하게 따른다는 점이 중요하다.** effort=low로 설정하면, 문제가 아무리 복잡해도 모델이 스스로 강도를 올리지 않고 low가 허용하는 만큼만 일한다("scopes its work to what was asked rather than going above and beyond"). 그래서 복잡한 구현 문제에 low를 쓰면 불충분한 사고(under-thinking)의 위험이 있다 — 공식 문서에서도 이런 증상이 보이면 프롬프트로 유도하지 말고 effort 자체를 `high`나 `xhigh`로 올리라고 명시하고 있다.
- 정리하면: adaptive thinking의 자동 판단도 결국 **effort라는 틀 안에서** 작동하는 것이지, effort를 무시하고 필요한 만큼 무한정 깊어지지는 않는다. "질문 난이도를 모델이 알아서 감지해서 effort까지 알아서 올려준다"는 기대는 틀린 것이다.

## Content Block 개념

Claude API 응답의 `content` 필드는 문자열 하나가 아니라 **여러 block으로 이루어진 배열**이다.

```json
{
  "role": "assistant",
  "content": [
    { "type": "thinking", "thinking": "..." },
    { "type": "text", "text": "..." }
  ]
}
```

왜 이렇게 설계했냐면, 텍스트·이미지·도구 호출·사고 과정처럼 성격이 다른 콘텐츠를 하나의 메시지 안에서 명확히 구분해서 다루기 위해서다. 문자열 하나로 뭉뚱그리면 "이 부분은 사고 과정이고 이 부분은 실제 답변이다"를 구분할 방법이 없다.

주요 block 타입:

| 타입 | 담는 내용 |
|---|---|
| `text` | 일반 텍스트 응답 |
| `thinking` | 모델의 추론 과정 |
| `redacted_thinking` | 안전상 이유로 편집(가려짐)된 추론 블록 |
| `tool_use` | 모델이 도구를 호출하겠다는 요청 |
| `tool_result` | 도구 실행 결과를 되돌려줄 때 쓰는 블록 |
| `image` | 이미지 입력 (주로 사용자 쪽에서 보냄) |
| `document` | PDF 등 문서 입력 |

하나의 응답 안에 여러 block이 순서대로 나올 수 있다 — thinking이 켜져 있으면 `thinking → text` 순서로, 도구를 쓰는 상황이면 `text → tool_use` 순서로 오는 식이다.

한 가지 확실히 짚은 오해 포인트: **thinking을 꺼도 다른 block 타입은 아무 영향을 받지 않는다.** `thinking: {type: "disabled"}`는 `thinking`이라는 특정 타입의 block 하나만 응답에서 빠지게 만들 뿐이고, `text`나 `tool_use`, `image` 같은 다른 block의 생성 여부와는 완전히 무관하다. thinking을 꺼도 최종 답변(`text`)이나 도구 호출(`tool_use`)은 화면에 정상적으로 나타난다.

## 비용 고려사항: Adaptive Thinking 사용 시 비용 구조

**총 출력 토큰 = Thinking 토큰 + 실제 응답 토큰**

thinking이 켜져 있으면, 화면에 보이든 안 보이든(`display` 설정과 무관하게) 추론 과정에 쓰인 토큰도 전부 output token으로 과금된다. 예를 들어 추론에 312토큰, 실제 응답에 36토큰을 썼다면 청구되는 output token은 둘을 합친 348토큰이다.

여기서 앞서 정리한 내용들이 자연스럽게 연결된다:

- thinking을 끄면(`type: "disabled"`) 이 추론 토큰 자체가 아예 발생하지 않으므로 비용이 줄어든다 — 다만 Sonnet 5/Opus 5에서는 앞서 말한 effort 제약이 있다.
- effort를 낮추는 것(low/medium)도 비용을 줄이는 방향이지만, thinking을 끄는 것과 달리 "얼마나 깊게 생각할지"만 조절할 뿐 thinking 자체를 없애지는 않는다.
- effort를 자주 바꾸는 것은 prompt cache를 무효화시켜 오히려 비용이 늘 수 있으므로, 세션 내내 적절한 기본값 하나로 유지하는 게 낫다.
- `MAX_THINKING_TOKENS` 환경변수로 정밀하게 토큰 상한을 걸어 비용을 통제하는 방식은 Sonnet 5 같은 adaptive-only 모델에서는 불가능하다 — `0`으로 완전히 끄는 것만 유효하고, `5000` 같은 특정 숫자는 무시된다. 고정 토큰 예산(`budget_tokens`) 개념은 Opus 4.6/Sonnet 4.6에만 남아있는 과도기 기능이기 때문이다.

결국 비용을 조절하는 실질적인 레버는 **effort 조정** 또는 **thinking 완전 비활성화** 두 가지로 좁혀지며, 세밀한 토큰 단위 제어는 현재 세대 adaptive-only 모델에서는 지원되지 않는다.

## 실습하며 나온 질문들

***Q). 소수 판별 알고리즘 3가지(에라토스테네스의 체, 밀러-라빈, 단순 나눗셈)의 시간복잡도를 비교하고, 100만 개 이하 소수를 구할 때 가장 효율적인 방법은?***  
A). 에라토스테네스의 체가 가장 효율적이다. 단순 나눗셈은 O(N√N), 체는 O(N log log N), 밀러-라빈은 개별 수 판별엔 빠르지만(O(k log³n)) 범위 전체를 구하려면 N번 반복해야 해서 오히려 비효율적이다. thinking on/off 상태에서 이 질문을 반복해서 던져보며 화면 차이(회색 이탤릭 사고 블록의 유무)도 직접 확인했다.

***Q). adaptive thinking mode가 켜져있지 않으면 thinking mode를 true로 설정해도 화면상 변화가 없어?***  
A). 아니다. legacy extended thinking만 지원하는 구형 모델(Haiku 4.5, Opus/Sonnet 4.5 이하)에서도 `/config thinking=true`는 동일하게 작동한다. Claude Code가 모델이 지원하는 방식(adaptive 우선, 없으면 legacy)을 자동으로 선택해서 사고 과정을 표시해주기 때문에, "adaptive thinking이 전제조건"이라는 가정은 틀렸다.

***Q). API 레벨에서 thinking을 disabled로 하면 모델이 내부적으로 전혀 추론을 하지 않고 응답하는 거야?***  
A). "추론 토큰을 생성하지 않는다"는 건 명시적인 thinking block(별도의 사고 과정 텍스트) 산출물이 없다는 뜻이지, 트랜스포머가 답변 토큰을 만들 때 거치는 신경망 연산(forward pass) 자체가 없다는 뜻은 아니다. 두 층위를 구분해야 한다 — 전자는 API에서 관찰·과금되는 명시적 산출물이고, 후자는 모델 구조상 항상 일어나는 암묵적 계산이다.

***Q). effort를 low로 하고서 복잡한 구현 문제를 질문하면 내부적으로 모델이 어떻게 동작해?***  
A). adaptive thinking은 여전히 작동은 하지만, effort가 지정한 범위 안에서만 추론한다. Sonnet 5는 effort 수준을 엄격히 따르기 때문에, 모델이 스스로 난이도를 보고 effort를 올려주지 않는다. 그래서 복잡한 문제에서 얕은 추론(under-thinking)이 나올 위험이 있고, 이럴 땐 프롬프트로 유도하기보다 effort 자체를 높이는 게 공식적으로 권장되는 방법이다.

***Q). 지금 쓰는 Sonnet 5 + adaptive thinking = true 상황에서, 토큰 예산을 설정하는 환경변수 MAX_THINKING_TOKENS도 유효해?***  
A). 절반만 유효하다. `0`으로 설정하면 thinking을 완전히 끄는 용도로는 유효하지만, `5000` 같은 0이 아닌 구체적인 숫자는 무시된다. 고정 thinking budget 개념 자체가 Opus 4.6/Sonnet 4.6에만 남아있는 과도기 기능이라, adaptive reasoning만 쓰는 Sonnet 5에서는 세밀한 토큰 상한 조절이 애초에 불가능하기 때문이다.

## 마무리

thinking mode를 처음엔 단순한 "화면 표시 스위치"로 이해했는데, 여러 번 되짚어보니 실제로는 추론 메커니즘 자체를 켜고 끄는 스위치였다. "화면에 안 보인다"와 "애초에 발생하지 않는다"를 구분하는 게 생각보다 중요했고, 이게 content block 구조와 비용 구조까지 다 연결되는 개념이라는 것도 오늘에서야 제대로 이해했다. 이런 세부 사항은 겉핥기로 넘어가면 계속 헷갈리는 부분이라, 오늘처럼 꼬리에 꼬리를 물고 확인해본 게 확실히 도움이 됐다.
