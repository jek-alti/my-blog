# 블로그를 웹앱 포트폴리오로 전환하기 — 서브에이전트 워크플로

오늘은 이 블로그를 단순한 글 모음에서 **미니 웹앱 포트폴리오**로 확장했다. 핵심은 `CLAUDE.md`를 새 작업 규칙으로 바꾸고, **서브에이전트**를 이용해 웹앱을 만드는 파이프라인을 세운 것이다. 그 흐름으로 실제 웹앱 2개(2048 게임, 픽셀 아트 에디터)까지 만들어 배포했다. 오늘 배운 것과 그 과정에서 궁금했던 것들을 정리한다.

## 1. CLAUDE.md를 "웹앱 게시용"으로 전환

기존 `CLAUDE.md`(마크다운 블로그 규칙)는 `CLAUDE_blog.md`로 백업하고, 웹앱 제작 워크플로를 담은 새 `CLAUDE.md`로 교체했다. 핵심은 **4단계 작업 사이클**이다.

| 단계 | 하는 일 |
| --- | --- |
| **Plan** | 서브에이전트로 계획(`spec.md`)을 세우고 사용자 승인을 받는다 |
| **Build** | 서브에이전트가 `/apps/{앱이름}/`에 독립적으로 구현한다 |
| **Review** | **별도** 서브에이전트가 검증하고 `review.md`를 작성한다 |
| **Embed** | 블로그 메인(`index.html`)에 웹앱 카드를 추가하고 깃 커밋한다 |

규칙의 핵심은 **"승인 없이 구현을 시작하지 않는다"** 와 **"Build와 Review 서브에이전트는 반드시 분리한다"** 였다.

## 2. 서브에이전트로 웹앱 2개 제작

같은 사이클로 두 개를 만들었다.

- **2048 게임** (`apps/2048/`) — 방향키·스와이프로 타일을 밀어 합치는 퍼즐. 점수판(현재/최고, `localStorage`).
- **픽셀 아트 에디터** (`apps/pixel-art/`) — 16×16 격자에 도트를 찍어 그림을 그리고 PNG로 저장. 색상 팔레트·지우개.

둘 다 프레임워크 없이 순수 HTML/CSS/JS로, 각 앱 폴더 안에 자체 완결되게 만들었다.

## 3. 실습하며 궁금했던 것들 (Q&A)

서브에이전트를 처음 다뤄보면서 나온 질문들을 정리했다.

**Q). Build와 Review 서브에이전트를 분리하면 내부적으로 무슨 일이 일어나나?**
A). 각 서브에이전트는 **독립된 새 컨텍스트(대화)** 로 실행된다. 메인 대화 내용을 물려받지 않고, 넘겨준 지침만 가지고 백지에서 시작한다. 자기 도구로 작업한 뒤 **최종 리포트만** 메인으로 돌려준다. Build와 Review를 분리하면, 검증자가 만든 사람의 가정을 물려받지 않으므로 **객관적인 검증**이 가능하다.

**Q). 서브에이전트가 도는 게 화면에 잘 안 보이는데 어떻게 확인하나?**
A). 새 창이 뜨는 게 아니라, 지금 대화 안에 **"Task"(에이전트) 항목**으로 중첩되어 나타난다. 실행 중엔 스피너, 끝나면 요약으로 바뀐다. 항목을 펼치면 그 에이전트가 넘겨받은 프롬프트(IN)와 실행한 도구 호출(Read/Write 등)이 보인다.

**Q). 화면 말고 확실하게 확인하는 방법은?**
A). 디스크에 로그가 남는다. 세션 폴더 아래 `subagents/agent-<agentId>.jsonl`에 서브에이전트별 전체 기록(시스템 프롬프트·도구 호출·결과)이 저장된다. 파일명의 agentId가 실행 시 반환된 값과 일치한다.

**Q). 서브에이전트가 쓴 토큰 수도 로그에 있나?**
A). 있다. 각 응답 기록의 `usage` 필드에 입력/출력/캐시 토큰이 남는다. 입력 토큰이 유난히 작게 보이는 건 대부분이 **캐시에서 재사용**(`cache_read`)되기 때문이다.

**Q). 에이전트 실행을 더 눈에 띄게 표시할 수 있나? (예: 그림 붙이기)**
A). 실제 이미지를 Task 블록에 붙이는 건 불가능하다. 그 UI는 도구가 그리는 것이라 스타일을 바꿀 수 없다. 대신 **에이전트 라벨(description)에 이모지**를 넣으면 화면에 그대로 보여서 눈에 띄게 만들 수 있다. (예: `🎄🔴🎄 REVIEW 🎄🔴🎄`)

**Q). git 그래프에 `main`이 두 개 보이는 이유는?**
A). 서로 다른 브랜치가 아니라 **로컬 `main`** 과 **원격 추적 `origin/main`** 이다. 푸시로 동기화되면 둘이 같은 커밋에 나란히 붙어 두 개로 보인다. 로컬이 앞서 있으면(`ahead`) 두 라벨이 서로 다른 커밋으로 떨어져 표시된다.

**Q). GitHub 배포 목록에 특정 커밋(2048)이 안 보이는 이유는?**
A). 배포 항목은 커밋 1개당이 아니라 **푸시(워크플로 실행) 1건당** 생긴다. 여러 커밋을 한 번에 푸시하면 워크플로가 한 번만 돌면서 **최신 커밋 이름**으로만 기록된다. 하지만 배포는 저장소 전체를 올리므로, 목록에 없어도 그 파일들은 **정상 배포**된다. (각 커밋을 따로 푸시하면 배포 기록도 따로 남는다.)

## 정리하며

오늘의 핵심은 **"Claude에게 무엇을 시킬까"에서 "Claude가 어떻게 일하게 만들까"로** 한 단계 올라간 것이다. `CLAUDE.md`로 작업 규칙을 정하고, 서브에이전트로 만들기와 검증을 분리하니, 웹앱 하나를 만드는 과정이 훨씬 체계적이 됐다. 이 블로그의 "웹앱" 섹션에서 오늘 만든 두 앱을 직접 해볼 수 있다. 🎮
