# 클로드 코드 명령어 총정리부터 GitHub 연동까지

오늘은 새로 배운 것보다 **흩어져 있던 것들을 정리하는 날**이었다. 슬래시 명령어·단축키를 표로 모으고, `/context`·`/clear`·`/compact`의 차이를 다시 짚고, CLAUDE.md가 실제로 어디에 저장되고 어떤 우선순위로 로드되는지 문서로 확인했다. 후반에는 GitHub Projects와 GitLens 같은 주변 도구, 그리고 지난번 만들어둔 `study-upload` 커맨드가 왜 안 먹혔는지까지 추적했다.

## 1. 슬래시 명령어와 단축키 표

책에 나온 두 표를 정리했다.

| 명령어 | 설명 |
| --- | --- |
| `/add-dir` | 추가 작업 디렉터리 지정 |
| `/memory` | CLAUDE.md 편집 |
| `/model` | AI 모델 선택/변경 |
| `/review` | 코드 리뷰 요청 |
| `/rewind` | 대화·코드 변경 되돌리기 |
| `/context` | 컨텍스트 사용량 시각화 |
| `/resume [세션]` | 이전 대화 재개 |
| `/rename <이름>` | 세션 이름 변경 |
| `/pr-comments` | PR 코멘트 확인 |

| 단축키 | 기능 |
| --- | --- |
| `Ctrl+C` | 세션 종료 |
| `Esc` | 응답 중단 |
| `Esc+Esc` | 이전 메시지로 되돌아가기 |
| `Opt+T` | Thinking 모드 Enabled/Disabled 확인 |
| `Shift+Tab` | 권한 모드 전환 (Normal→Auto-accept→Plan) |
| `Ctrl+L` | 터미널 화면 정리 |
| `Ctrl+R` | **셸** 명령어 히스토리 검색 (대화 목록 아님) |

## 2. 컨텍스트 관리: `/context` vs `/compact` vs `/clear`

| 명령어 | 하는 일 | 대화 기록 |
| --- | --- | --- |
| `/context` | 사용량을 색상 그리드로 시각화(조회만) | 유지 |
| `/compact` | 요약해서 압축, `/compact <지침>`으로 강조점 지정 가능 | 요약된 형태로 유지 |
| `/clear` | 완전 초기화 | 삭제 (CLAUDE.md는 유지) |

컨텍스트가 꽉 차면 `/context`로 확인 → `/compact`로 압축, 주제가 완전히 바뀌면 `/clear`가 기본 흐름이다.

## 3. 프롬프트 특수기호와 실행 모드

- `@파일` (Tab 자동완성), `!명령어`(Bash 직접 실행), `# 내용`(CLAUDE.md에 즉시 기록)
- 실행 모드: 대화형(`claude`) / Print(`claude -p "..."`, 파이프·CI 연동 가능)
- YOLO 모드(`--dangerously-skip-permissions`): 승인 없이 실행, 위험 요소 있음
- 권한 세분화: `--allowedTools "Read,Write,Bash(npm run lint:*)"` 처럼 도구별·패턴별로 허용 범위를 좁힐 수 있다.

## 4. 실습: `test.json` 만들며 만난 Permission 경고

`--allowedTools`로 파일을 생성/조회하는 실습에서 매번 아래 3줄 경고가 떴다.

```
Permission deny rule (.../.claude/settings.json): Write(~/.claude/settings.json) is not matched by file permission checks — only Edit(path) rules are.
```

원인은 실습 실패가 아니라, **전역 `settings.json`의 규칙이 `Write(path)`로 적혀 있는데 파일 수정 도구는 `Edit(path)` 규칙으로만 검사되기 때문**이었다. 즉 규칙 자체가 매칭되지 않아 무시된 것. `test.json` 생성·조회는 정상 동작했다.

## 5. CLAUDE.md는 어디에 있고, 뭐가 우선하는가

유형별 메모리 위치([표 2-10])와 전역/프로젝트 디렉터리 구조([표 2-11], [표 2-12])는 [클로드 코드 지침과 설정 파일](claude-code-config-files) 글에 소제목으로 추가해 정리했다. 오늘 추가로 확인한 것은 **모델 설정의 우선순위**다: `/model`(세션 중) > `--model` 플래그 > 환경변수 `ANTHROPIC_MODEL`(`.zshrc`) > `settings.json`의 `model` 필드. `.zshrc`에 환경변수를 잡아두면 `/config model=...`로 저장한 값보다 우선 적용된다.

## 6. `.claude/rules/`와 `@import` — 둘 다 CLAUDE.md 비대화 대책이지만 성격이 다르다

| 목적 | 방법 | 컨텍스트 절약 |
| --- | --- | --- |
| 파일을 주제별로 나눠 관리 편하게 | `@경로` import | ❌ (import된 내용도 세션 시작 시 전부 로드됨) |
| 특정 파일 작업할 때만 규칙 로드 | `.claude/rules/*.md`의 `paths:` frontmatter | ✅ (매칭되는 파일을 읽을 때만 로드) |

`.claude/rules/`는 책 예시(`api-rules.md`, `component-rules.md`)처럼 실제로 공식 기능이었고, "자동 적용"도 관례가 아니라 진짜 조건부 로딩이었다.

## 7. GitHub Projects와 GitLens

- **GitHub Projects**: 여러 저장소의 이슈·PR을 한 칸반보드에 모아 관리하는 도구. Project는 레포에 종속되지 않으므로 접근 권한만 있으면 서로 다른 레포의 이슈를 한 보드에 섞을 수 있고, `Workflows → Auto-add to project`로 자동화도 가능하다.
- **이슈가 검색 안 될 때**: 레포에 이슈가 아예 없거나 Issues 기능이 꺼져 있는 경우다. `Settings → General → Features → Issues`를 확인하면 된다.
- **GitLens Commit Graph**: `Cmd+Shift+P` → `GitLens: Show Commit Graph`로 여는 게 가장 확실하다.

## 8. `study-upload` 커맨드가 안 먹은 이유

지난번 만들어둔 `shared-harness/commands/study-upload.md`를 `study_upload`(언더스코어)로 입력해서 실패했다. 실제 이름은 `study-upload`(하이픈)이고, 게다가 이 파일은 `my-blog/.claude/commands/`와 `claude-code-master/.claude/commands/`에만 있어서 그 폴더 안에서 `claude`를 실행해야 보인다. 지금 세션처럼 상위 폴더(`study/`)에서 열면 프로젝트 커맨드 자체가 로드되지 않는다.

## 실습하며 나온 질문들

***Q). deploy.md는 Vercel 배포만 해당되는 거야?***  
A). 아니다. `deploy.md`는 그냥 커스텀 커맨드 파일일 뿐이라 이름·내용은 프로젝트가 정하는 대로다. 책 예시가 Vercel을 쓴 것뿐이고, AWS·Netlify·사내 서버 등 어떤 배포 방식이든 그 절차를 문서화해서 넣으면 된다.

***Q). Next.js와 Node.js의 차이가 뭐야?***  
A). Node.js는 JS를 브라우저 밖에서 실행하는 런타임(V8 엔진 + 파일시스템·네트워크 API)이고, Next.js는 그 위에서 동작하는 React 프레임워크다. Python과 Django의 관계에 비유할 수 있다.

***Q). .claude/rules/ 폴더 역할이 뭐야?***  
A). CLAUDE.md 하나에 규칙을 몰아넣지 않고 주제별로 나눠 관리하는 폴더다. `paths:` frontmatter로 특정 glob 패턴에 매칭되는 파일을 열 때만 그 규칙이 자동으로 컨텍스트에 로드되는, 실제 조건부 로딩 기능이다.

***Q). CLAUDE.md가 길어지지 않게 @import를 쓰라는데, 설명과 예시?***  
A). `@경로/파일` 형태로 다른 파일을 참조하면 그 내용이 그 자리에 펼쳐져 로드된다. 다만 import된 내용도 세션 시작 시 전부 로드되므로 **컨텍스트 절약 효과는 없고, 파일을 주제별로 나눠 관리하기 편해지는 것**이 핵심 이점이다. 컨텍스트를 실제로 아끼려면 `.claude/rules/`의 `paths:` frontmatter를 써야 한다.

***Q). 지금 thinking mode 설정값이 뭐야?***  
A). `settings.json`에 `thinking` 키가 명시되어 있지 않으면 기본값 상태다. `/config`는 조회가 아니라 설정(set) 전용이라, 실제 상태를 보려면 `Opt+T`로 Enabled/Disabled를 직접 확인해야 한다.

***Q). 지금까지 입력한 대화 목록을 보려면?***  
A). `/resume`을 인자 없이 입력하면 세션 목록 선택 화면이 열린다. `Ctrl+R`은 대화 목록이 아니라 셸의 명령어 히스토리 검색이라 서로 다른 기능이다.

***Q). .zshrc의 ANTHROPIC_MODEL 환경변수와 설정 파일의 model 필드는 무슨 관계야?***  
A). 우선순위는 `/model`(세션 중) > `--model` 플래그 > 환경변수 `ANTHROPIC_MODEL` > `settings.json`의 `model` 필드다. `.zshrc`에 환경변수를 심어두면 `/config model=...`로 저장해둔 값보다 항상 이긴다.

***Q). handoff.md 파일에 대해 설명해줘.***  
A). Claude Code의 공식 내장 파일은 아니고, 세션 종료 직전(특히 `/clear` 전에) 진행 상황·결정 사항·남은 작업을 적어 다음 세션에 인계하는 관례적 문서다. 실제로 컨텍스트 관리 다이어그램에도 "종료 직전 HANDOFF.md로 인계"가 `/compact`·`/clear`와 나란히 워크플로 마지막 단계로 그려져 있었다.

***Q). --continue의 예제를 알려줘.***  
A). `claude --continue` 또는 `claude -c`로 가장 최근 세션을 선택 화면 없이 즉시 이어간다. `--resume`은 여러 세션 중 골라야 할 때, `--continue`는 바로 직전 것 하나만 빠르게 이어갈 때 쓴다.

***Q). --continue로 이어갈 때 토큰 소비량은 어느 정도야?***  
A). 재개 시점에 저장돼 있던 대화 전체가 다시 컨텍스트로 들어가므로, 끝냈을 때의 누적 사용량과 비슷한 규모다. 비용은 프롬프트 캐싱 여부에 갈리는데, 캐시 유효 시간(구독 플랜 1시간, API/usage credit 5분) 안에 재개하면 저렴한 캐시 읽기 요율이 적용되고, 그 시간을 넘기면 캐시 미스로 전체를 정가로 재처리한다.

***Q). GitHub에서 Project를 만드는 이유가 뭐야?***  
A). 이슈·PR을 칸반보드로 시각화하고, 여러 레포의 작업을 한 보드에 모아 관리하기 위해서다. 코드 저장(Repository)과 작업 관리(Project)를 분리하는 도구라고 보면 된다.

***Q). 기존에 만들어둔 my-blog 레포에서 이슈 검색이 안 되는데, 이슈는 어떻게 만들어?***  
A). 레포에 이슈가 하나도 없거나 Issues 기능이 꺼져 있어서다. Project의 "Add items" 검색창에 제목을 입력하면 뜨는 "Create new issue" 옵션을 쓰거나, 레포의 Issues 탭에서 직접 New issue로 만들면 된다.

***Q). gitlens graph를 보고 싶은데 어디를 설정하면 돼?***  
A). `Cmd+Shift+P` → `GitLens: Show Commit Graph`가 가장 확실하다. Source Control 뷰 툴바나 하단 패널 탭에도 진입점이 있을 수 있다.

***Q). study_upload 커맨드가 안 먹는데?***  
A). 실제 파일명이 `study-upload`(하이픈)인데 `study_upload`(언더스코어)로 입력했고, 게다가 이 커맨드는 `my-blog`·`claude-code-master` 폴더의 `.claude/commands/`에만 있어서 그 폴더 안에서 세션을 열어야 로드된다.

## 마무리

오늘은 새로운 기능을 배우기보다, 그동안 파편적으로 알고 있던 명령어·설정·주변 도구를 한 번씩 문서로 다시 확인하는 날이었다. 특히 `/model` 우선순위나 `.claude/rules/`의 자동 로딩처럼 "관례인지 실제 기능인지" 헷갈렸던 부분들을 공식 문서로 직접 검증한 게 오늘의 가장 큰 수확이다.
