# 스킬을 제대로 다뤄보기 — 커맨드 구분부터 마켓플레이스 설치, 실전 계획서 작성, Codex 검증까지

며칠에 걸쳐 "스킬(Skill)"을 실습 주제로 잡았다. 처음엔 스킬과 슬래시 커맨드를 헷갈리는 것부터 시작해, 마켓플레이스·CLI로 스킬을 직접 설치해보고, 검색 결과와 실제 레포가 다를 수 있다는 걸 겪고, 보안 스캔 결과로 설치를 보류하는 판단까지 해봤다. 마지막엔 설치한 스킬 두 개(계획 수립·문서 생성)를 실제로 조합해 To-Do 앱 계획서를 만들고, Codex에게 검증받아 FAIL 피드백을 반영하는 것까지 이어졌다.

## 스킬 vs 슬래시 커맨드

`study-upload`를 스킬이라고 착각했는데, 실제로는 슬래시 커맨드였다.

| | 슬래시 커맨드 | 스킬 |
|---|---|---|
| 저장 위치 | `.claude/commands/이름.md` | `.claude/skills/이름/SKILL.md` |
| 형태 | 파일 1개 | 폴더(SKILL.md + 참고파일 등) |
| 발동 방식 | 사용자가 직접 `/이름` 입력 | Claude가 상황 보고 알아서 판단해 발동 |

핵심은 "누가 부르냐"다. 커맨드는 내가 불러야 뜨고, 스킬은 Claude가 설명문의 트리거 조건을 보고 스스로 꺼내 쓴다.

## 플러그인 마켓플레이스로 스킬 설치하기

`canvas-design`이라는 스킬을 예로 실습했다. claude.ai 앱 채팅에는 기본으로 있는데 Claude Code에는 없어서, 직접 설치해봤다.

1. `/plugin marketplace add anthropics/skills`
2. `/plugin install example-skills@anthropic-agent-skills`
3. `/reload-plugins`

하나의 마켓플레이스 안에 **여러 플러그인**이 있고, 각 플러그인은 **여러 스킬을 번들**로 묶는다는 걸 배웠다. 처음에 무심코 `claude-api` 플러그인을 설치했는데 `canvas-design`이 안 보여서, `marketplace.json`을 직접 열어 원인을 찾았다. 설치 여부는 `~/.claude/settings.json`의 `enabledPlugins`와 캐시 폴더의 `SKILL.md` 존재로 교차 확인했다.

## Cowork vs Claude Code — 어디서 실행되는가

책에서는 Cowork가 "서버에 가상의 미니컴퓨터를 만들어 작업하고, 끝나면 다 사라진다"고 설명했다. 이게 로컬 Claude Code에도 해당되는지 물어봤는데, 답은 정반대였다.

| | Claude Code | Cowork |
|---|---|---|
| 실행 위치 | 사용자의 실제 로컬 컴퓨터 | Anthropic 서버의 임시 가상환경 |
| 작업 결과 | 계속 누적·잔존 | 세션 종료 시 폐기 |

이 차이는 뒤에서 `docx` 스킬을 쓸 때 다시 한번 실감했다 (아래 참고).

## 세션은 자동으로도 이어진다

VSCode를 껐다 켰는데 이전 대화가 그대로 남아 있었다. 세션 파일을 열어보니 파일 자체는 새로 생성됐지만 내용은 자동으로 이어붙어 있었다.

| | VSCode 재시작(자동 이어붙이기) | `/resume` |
|---|---|---|
| 트리거 | 자동 | 사용자가 직접 입력 |
| 선택권 | 없음(가장 최근 것만) | 과거 세션 목록에서 선택 가능 |
| 세션 파일 | 새 파일 생성, 내용만 이어받음 | 선택한 세션 파일을 그대로 재사용 |

자동 이어붙이기든 `/resume`이든, 과거 대화가 컨텍스트에 실리면 이후 매 턴마다 그 전체가 다시 입력 토큰으로 전송된다. 다만 프롬프트 캐싱(유효시간 1시간) 덕분에 짧은 시간 안에 이어지는 요청은 훨씬 저렴하게 처리된다. 캐싱이 적용되는 이유는 "빨리 재시작해서"가 아니라 "마지막 요청 이후 경과 시간이 캐시 유효시간 안에 들어왔기 때문"이라는 걸 정확히 짚었다.

## 스킬 CLI로 직접 찾고 설치해보기

`npm install -g skills`로 skills.sh CLI를 설치해서 `skills find`, `skills add`를 실습했다. 여기서 중요한 교훈을 하나 얻었다: **검색 결과가 항상 정확하진 않다.** `skills find planner`로 나온 `shubhamsaboo/awesome-llm-apps@project-planner`(4.4K installs)를 설치하려 했지만, 실제로 그 레포를 클론해보니 `project-planner`라는 스킬은 없었다 — 검색 인덱스가 오래됐거나 잘못됐던 것이다. 다운로드 수·출처만 믿지 말고 실제 레포를 열어 확인해야 한다는 스킬 품질 체크리스트를 실전으로 겪은 셈이다.

설치 과정에서 CLI가 "어느 에이전트에 설치할지"를 물었는데, 여기서도 오해할 뻔한 지점이 있었다.

- **Universal(`.agents/skills`)** — 여러 에이전트 도구가 공유하는 표준 폴더. Amp, Cursor, Codex 같은 이름들이 나열되지만, 이건 그 프로그램들을 설치하는 게 아니라 "저 도구들이 이 공용 폴더를 스킬 저장소로 함께 쓴다"는 뜻이다.
- **Additional agents** — Claude Code처럼 자기만의 폴더(`.claude/skills`)를 쓰는 도구는 따로 체크해야 한다.

실제로 설치해보니 `.claude/skills/<스킬명>`은 파일이 복사된 게 아니라 `.agents/skills/<스킬명>`을 가리키는 **심볼릭 링크**였다 — 중복 저장 없이 여러 도구가 원본 하나를 공유하는 구조였다.

설치 전에는 CLI가 자체 보안 스캐너(Gen), Socket, Snyk 세 가지 결과를 보여줬다. `advisor-orchestrator-worker`는 Snyk가 "Med Risk"로 표시해서, 다른 지표가 안전해도 하나라도 걸리면 설치를 보류하는 판단을 했다. 대신 검색으로 찾은 `addyosmani/agent-skills@planning-and-task-breakdown`(19.1K installs, 신뢰할 만한 개발자)을 설치했다.

## planning-and-task-breakdown 스킬 살펴보기

설치한 스킬의 SKILL.md를 직접 열어 핵심을 확인했다: 큰 작업을 의존성 그래프로 파악하고, 수평이 아닌 **수직으로 슬라이스**해서(DB→API→UI를 한꺼번에 만들지 않고 기능 하나를 끝까지), 각 작업에 수용 기준·검증·의존성·규모를 명시하는 절차다. "작업 제목에 '그리고'가 들어가면 사실 두 작업"이라는 규칙이 인상적이었다. 이 스킬을 한국어로 번역해 `SKILL.ko.md`로 만들어 설치된 스킬 폴더 안에 같이 두었다.

## 두 스킬을 결합해 실전 계획서 만들기

`planning-and-task-breakdown`의 절차와 `docx` 스킬을 결합해 "To-Do 리스트 앱" 구현 계획서를 실제로 만들어봤다. 여기서 다시 Cowork와 로컬의 차이를 체감했다 — `docx` 스킬 지침은 "`docx` npm 패키지가 미리 설치되어 있다"고 가정하는데, 그건 Cowork 같은 사전 세팅된 샌드박스 기준이었고 로컬 환경에는 없어서 직접 설치해야 했다. PDF 렌더링 검증에 필요한 LibreOffice도 로컬에 없어서, 대신 `pandoc`으로 텍스트·표 구조가 깨지지 않았는지 확인하는 방식으로 대체했다.

완성한 계획서는 `doc/todo-list-plan.md`와 `doc/todo-list-plan.docx` 두 형식으로 저장했다.

## Codex로 계획서 검증받기

만든 계획서를 Codex에게 검증받았더니 **FAIL** 판정이 나왔다. 주요 피드백:

| 문제 | 요지 |
|---|---|
| Review·Embed 단계 누락 | CLAUDE.md가 요구하는 Review(`review.md`)·Embed(앱 카드 추가) 단계가 계획에 없음 |
| 팔레트 연동 방식 불명확 | "변수 참조"만 있고 실제 방식(로컬 `:root` 정의 vs 링크)이 안 정해짐 — 기존 앱들은 로컬 정의 방식을 씀 |
| localStorage 처리 미구체화 | 저장 키·데이터 형식·손상 데이터 처리가 위험표에만 있고 실제 작업이 없음 |
| 작업 1 규모 오산정 | 파일 3개짜리인데 "S"로 표기됨 |
| 접근성 기준 부재 | 라벨링·키보드 조작·포커스 관리 기준이 없음 |
| 작업 순서 어긋남 | 사용법 안내(필수 요구사항)가 뒤로 미뤄져 있음 |

이 피드백을 전부 반영해 계획서를 v2로 다시 썼다 — Review·Embed를 작업으로 추가하고, 팔레트·저장소 방식을 저장소의 실제 관례(`apps/pixel-art`의 try/catch 패턴 등)에 맞춰 확정하고, 규모와 접근성 기준을 보강했다.

## 실습하며 나온 질문들

***Q). canvas-design이라는 스킬은 어떻게 다운받아?***  
A). Anthropic 공식 레포(`anthropics/skills`)를 마켓플레이스로 추가한 뒤, `canvas-design`이 포함된 `example-skills` 플러그인을 설치하면 된다.

***Q). "클로드가 알아서 프로그램을 설치·실행하고, 끝나면 사라진다"는 설명이 로컬 Claude Code나 클로드앱 Cowork 모두에 해당돼?***  
A). Cowork에만 해당한다. Claude Code는 반대로 사용자의 실제 로컬 컴퓨터를 직접 조작해서 결과가 계속 남는다.

***Q). VSCode를 종료했다 다시 열었을 때, 마지막 세션을 자동으로 resume한 거야?***  
A). 완전히 같은 세션은 아니고, 새 세션 파일을 만들면서 이전 대화 내용을 자동으로 이어붙인 것이다.

***Q). 지금 이어붙이기 한 동작도 /resume처럼 과거 내용을 읽느라 토큰을 쓴 거야?***  
A). 그렇다. 컨텍스트에 과거 대화가 실리는 순간, 이후 매 턴마다 그 전체가 다시 입력 토큰으로 전송된다.

***Q). 지금은 VSCode를 아주 빨리 종료 후 재시작했으니 프롬프트 캐싱이 적용돼 싸게 처리된 경우야?***  
A). 결과적으로는 맞지만, 정확한 이유는 "빨리 재시작해서"가 아니라 "마지막 API 요청 이후 경과 시간이 캐시 유효시간(1시간) 안에 들어왔기 때문"이다.

***Q). skills find로 찾은 project-planner를 설치하려는데 안 됐어. 왜 그런 거야?***  
A). 검색 인덱스에는 나왔지만 실제 레포를 클론해보니 그 이름의 스킬이 없었다. 검색 결과의 다운로드 수나 출처만 믿지 말고 실제 레포 내용을 확인해야 한다는 걸 보여준 사례다.

***Q). Claude Code를 선택하면 .agents/skills, .claude/skills 두 폴더에 스킬 파일이 각각 생성되는 게 맞지?***  
A). 두 곳에 다 나타나긴 하지만, 파일이 복사되는 게 아니라 `.claude/skills` 쪽은 `.agents/skills`를 가리키는 심볼릭 링크로 생성된다.

***Q). advisor-orchestrator-worker의 핵심 기능을 설명해줘.***  
A). 어드바이저(전략·위험평가)·조율자(계획·위임)·워커(저비용 병렬 실행) 세 계층으로 대규모 작업을 나눠 처리하는 오케스트레이션 패턴이다.

***Q). 이 계획을 Codex를 통해서 검증해줘봐.***  
A). FAIL 판정을 받았다. Review·Embed 단계 누락, 팔레트·저장소 방식 불명확, 규모 오산정, 접근성 기준 부재가 핵심 피드백이었고, 전부 반영해 계획서를 v2로 다시 작성했다.

## 마무리

스킬이라는 주제로 시작했지만, 결국 반복해서 마주친 질문은 "이게 실제로 검증된 정보인가, 아니면 그럴듯해 보이는 추정인가"였다. 검색 결과에 나온 스킬이 실제로는 없었던 것, 보안 스캐너 하나가 위험을 알렸을 때 설치를 멈춘 것, 계획서를 Codex에게 검증받아 FAIL을 받고서야 빠진 부분이 드러난 것 — 전부 같은 맥락이다. 그럴듯한 결과물도 별도의 검증 단계를 거치지 않으면 믿을 수 없다는 걸 이번 실습에서 여러 번 확인했다.
