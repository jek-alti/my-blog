# 창을 닫아도 세션이 살아있게 — 리모트컨트롤과 tmux

오늘은 Claude Code를 폰에서 원격 조종하는 **리모트컨트롤**을 테스트하다가, 자연스럽게 **tmux**까지 익혔다. 핵심 질문은 하나였다. "터미널 창을 닫으면 세션은 어떻게 되는가?" 일반 터미널에서는 창을 닫자 세션이 종료·보관됐고, tmux를 끼우자 창을 닫아도 세션이 살아남았다. 그 차이의 정체를 프로세스 수준에서 눈으로 확인한 하루였다.

## 일반 터미널: 창이 곧 프로세스

처음엔 그냥 터미널에서 `claude`를 띄워 두고 창을 닫아봤다. 결과는 폰에 "세션이 종료되며 보관되었다"는 메시지. 이유는 단순하다. 일반 터미널에서는 **창(터미널)이 claude 프로세스를 직접 붙잡고 있다.** 그래서 창을 닫으면 프로세스도 같이 죽는다. 대화 기록은 남으니 나중에 `claude --continue`나 `claude --resume`으로 다시 열 수는 있지만, 그 순간의 살아있는 세션은 사라진다.

## tmux: 서버(방)와 클라이언트(창)의 분리

tmux는 이 구조를 바꾼다. 핵심은 **두 가지가 따로 논다**는 점이다.

- **서버(session)**: 실제 프로그램(claude)이 돌아가는 백그라운드 "방". 화면이 있든 없든 혼자 살아있다.
- **클라이언트(client)**: 그 방을 들여다보는 "창(터미널)". 사람이 보고 입력하는 통로일 뿐이다.

즉 방은 방대로 돌아가고, 창은 그 방을 비추는 모니터다. 창을 닫아도 방은 안 꺼진다. 이 구조 덕에 터미널을 닫아도 claude가 살아있는다.

```
[터미널 창] ── attach ──> [tmux 세션(cc)] ── 실행 ──> [claude]
  (클라이언트)              (백그라운드 방)
```

### 기본 명령

```
tmux new -s cc        # 'cc'라는 이름으로 세션(방)을 처음 만들 때 한 번
tmux attach -t cc     # 이미 있는 세션에 다시 붙을 때 (-t = target)
tmux ls               # 세션 목록·상태 확인
tmux kill-server      # 서버까지 완전 종료
```

`-s`는 session name, `-t`는 target이다. `cc`는 특별한 뜻이 아니라 그냥 내가 붙인 별명이라 `work`든 `myblog`든 뭐든 된다. 이미 있는 세션에 `tmux new`를 또 하면 `duplicate session` 에러가 나므로, 다시 들어갈 땐 반드시 `attach`를 쓴다.

### detach는 종료가 아니다

가장 헷갈린 부분. tmux에서 빠져나오는 건 `Ctrl+C`가 아니다.

| 키 | 하는 일 |
|----|---------|
| `Ctrl+C` | 지금 실행 중인 **앱(claude)에 중단 신호** — claude가 종료됨 |
| `Ctrl+b` 뗀 뒤 `d` | tmux에서 **분리(detach)** — 창만 떨어지고 claude는 살아있음 |

처음에 `Ctrl+C`로 빠져나왔더니 claude만 종료되고 tmux 셸로 떨어졌다. 제대로 detach 하면 `[detached (from session cc)]` 메시지가 뜨고 원래 터미널로 돌아온다.

## 상태를 눈으로 읽는 법

### tmux ls의 (attached) 여부

```
cc: 1 windows (created ...) (attached)   ← 보는 창 있음
cc: 1 windows (created ...)              ← (attached) 없음 = detached
```

tmux는 detached일 땐 아무 표시를 안 하고, attached일 때만 `(attached)`를 붙인다. 이 한 줄로 "세션은 살아있고 보는 창만 떨어졌는지"를 알 수 있다.

### 프로세스 개수 = 서버 1 + 클라이언트 N

`pgrep -fl tmux`를 attach 상태에서 보면 프로세스가 2개, detach 후엔 1개로 줄었다. 공식으로 정리하면:

```
tmux 프로세스 수 = 서버 1개 + (붙어있는 터미널 수만큼) 클라이언트
```

- 2개 = 서버 1 + 클라이언트 1 → attached
- 1개 = 서버 1 + 클라이언트 0 → detached (방만 살아있음)

detach하자 클라이언트만 죽고 **서버는 그대로 남는 걸** PID로 직접 확인했다. 즉 detach해도 claude는 안 죽는다는 게 개수 변화로 증명된 셈이다. 개수를 세는 것보다 역할로 보고 싶으면 `tmux list-clients`로 붙어있는 클라이언트만 딱 확인할 수도 있다.

## 리모트컨트롤 연결의 진짜 조건

여기서 오늘의 핵심 결론이 나왔다. **폰 리모트컨트롤이 붙는 대상은 `claude` 프로세스지, 터미널도 tmux도 아니다.**

| 동작 | claude 프로세스 | 폰 연결 |
|------|----------------|---------|
| `Ctrl+C` (claude 종료) | 죽음 | 끊김 |
| `Ctrl+b d` (detach) | 살아있음 | 유지 |
| 창 닫기 (detach 상태) | 살아있음 | 유지 |

그래서 컴퓨터를 떠날 때 **claude를 종료하지 말고 detach만** 하면, claude는 tmux 안에서 계속 살아 폰에서 원격 조종이 이어진다. 돌아와서는 `tmux attach -t cc`로 그 화면 그대로 복귀한다. tmux 서버를 `kill-server`로 죽이면 그 안의 claude도 함께 강제 종료되지만, 대화 기록은 남아 `claude --resume`으로 다시 이을 수 있다.

## 실습하며 나온 질문들

***Q). tmux 프로세스가 살아있는 건 어디에서 확인해?***  
A). `tmux ls`로 세션 목록을, `pgrep -fl tmux`로 프로세스를, `pgrep -fl claude`로 claude 생존을 본다. 가장 확실한 건 `tmux attach -t cc`로 다시 붙어 화면을 눈으로 확인하는 것.

***Q). 세션이 attached 상태라는 건 정확히 무슨 의미야?***  
A). 세션(방)에 터미널 창이 연결돼 지금 누군가 그 방을 보고 있다는 뜻이다. detached는 세션은 살아있지만 보는 창이 없는 상태로, 방 안 프로그램은 계속 돌아간다.

***Q). tmux attach -t cc에서 cc가 뭐야?***  
A). 세션 이름이다. `tmux new -s cc`로 만들 때 붙인 별명이라, 다시 붙을 때 같은 이름으로 찾는 것이다. 이름이 기억 안 나면 `tmux ls`에서 콜론 앞에 있는 게 세션 이름이다.

***Q). 별도 터미널에선 tmux 프로세스가 2개, tmux 안에선 1개로 보이는데 차이가 뭐야?***  
A). tmux는 항상 서버 1개 + 붙어있는 창 수만큼의 클라이언트로 구성된다. 개수가 곧 "그 세션을 보는 창이 몇 개냐"를 뜻한다. detach하면 클라이언트만 죽고 서버는 남는다.

***Q). Ctrl+C로 claude를 빠져나가면 폰에서 더 이상 연결이 안 되는 거지?***  
A). 맞다. 리모트컨트롤은 claude 프로세스에 붙기 때문에, Ctrl+C로 프로세스를 죽이면 tmux 서버가 살아있어도 붙을 대상이 없어져 연결이 끊긴다. 떠날 땐 종료 대신 detach를 해야 한다.

## 마무리

지난번 "창=프로세스"라 창을 닫으면 죽던 구조가, tmux를 끼우니 "서버가 프로세스를 붙잡아 창을 닫아도 사는" 구조로 바뀌는 걸 프로세스 개수까지 직접 세어가며 확인했다. 결국 리모트컨트롤을 유지하는 패턴은 한 줄로 압축된다 — **떠날 땐 detach, 돌아오면 attach.** 도구의 동작을 외우는 대신 "무엇이 프로세스를 붙잡고 있는가"라는 한 축으로 이해하니 전부 연결됐다.
