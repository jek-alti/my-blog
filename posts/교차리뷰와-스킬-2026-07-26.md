# 제작 AI와 평가 AI를 분리하기 — Gemini·Codex 교차 리뷰와 스킬

오늘은 "만드는 AI ≠ 평가하는 AI"라는 원리를 실제로 구축했다. Claude Code가 만든 코드를 **다른 AI(Codex)** 에게 헤드리스로 리뷰시키고, 그 지적을 반영→재리뷰하는 루프를 PASS가 나올 때까지 돌렸다. 그 과정에서 Gemini/Codex CLI를 설치·인증하며 겪은 트러블슈팅과, 이 하네스를 스킬로 패키징하는 방법까지 배웠다.

## 1. 왜 제작 AI와 평가 AI를 분리하나

한 AI에게 자기비판을 시키는 것보다, **별도의 엄격한 평가 전담 AI**를 두는 게 더 쉽고 효과적이다. 특히 **다른 모델**을 평가자로 쓰면 제작 모델의 습관·편향까지 벗어난다.

```
[ 한 AI가 자기검증 ]          [ 제작 AI  ⟂  평가 AI 분리 ]
자기 가정에 갇히기 쉬움   →   독립적·엄격한 시선으로 결함 포착
```

우리 구조: **Claude Code(제작)** 가 코드 리뷰를 요청하면 → **Codex/Gemini(평가)** 가 리뷰해 보고서(`codex-review.md`)로 제출한다.

## 2. Gemini CLI 셋업과 트러블슈팅

| 단계 | 요점 |
| --- | --- |
| 설치 | `npm install -g`는 `/opt/homebrew` 권한(EACCES)으로 막힘 → **brew로 설치가 정석** |
| 인증 3방식 | ① Google 로그인 ② API 키(AI Studio) ③ Vertex AI |
| OAuth 내부동작 | 브라우저 동의 → 인가 코드 → 토큰 교환 → `~/.gemini/oauth_creds.json`에 캐싱 |
| 무료 티어 차단 | Google 로그인(무료 Code Assist 개인 티어)이 `UNSUPPORTED_CLIENT`로 막힘 → **API 키로 우회** |

배운 점: **인증 경로 하나가 막히면 대안 경로(키)로 전환**하는 게 실전 트러블슈팅이다.

## 3. Codex CLI + codex-plugin-cc

- `codex-plugin-cc`는 Claude Code 안에서 Codex를 부르는 **공식 플러그인**. 단 `/plugin`·`/codex:*` 명령은 **CLI(터미널)에서만** 동작하고 VS Code 확장에선 미지원.
- Codex 로그인은 **device-auth**(디바이스 코드 확인) 방식.
- **direct 모드** = 명령마다 Codex를 직접(1회성) 호출 / **공유 런타임** = 백그라운드 상주 서버(지속·병렬 작업용).
- **review-gate**(`--enable-review-gate`) = "작업 종료 전 리뷰 필수"를 **Stop 훅**으로 강제 — 전에 배운 훅(PreToolUse=실행 전, Stop=종료 전)과 같은 개념.

## 4. 서브에이전트로 Codex 교차 리뷰 실행

확장에서도 되는 방법: **서브에이전트가 `codex exec`(헤드리스)를 직접 호출**한다. Codex는 read-only 샌드박스로 저장소를 스스로 읽고 평가하며, 결과만 `codex-review.md`에 저장한다.

```bash
codex exec "당신은 엄격한 코드 리뷰어입니다. apps/{앱}/ 코드를 리뷰하고, 기존 review.md에 없는 추가 문제를 심각도·위치와 함께 보고하세요."
```

## CLI 헤드리스 모드와 direct 모드는 다른 축이다

오늘 두 용어가 다 나왔는데, 이름이 비슷해 헷갈리기 쉽다. 사실 **서로 다른 층위**를 가리킨다.

### CLI 헤드리스(headless) 모드 — "어떻게 실행하나"
CLI를 **대화형 화면 없이 한 번에 실행**하는 방식이다. 프롬프트를 주면 결과만 출력하고 끝난다.

- 예: `gemini -p "..."`, `codex exec "..."`
- 반대는 **대화형(interactive)**: `gemini`/`codex`만 치면 TUI 세션이 열려 계속 주고받는다.
- 쓰임: 자동화·스크립트, 그리고 **다른 프로그램(Claude Code 서브에이전트)이 호출**하기에 적합.

### direct 모드 — "백엔드를 어떻게 굴리나" (Codex 플러그인)
Codex를 호출할 때 **매번 직접(1회성)** 실행하는 방식이다.

- 반대는 **공유 런타임(shared runtime)**: 백그라운드에 **상주하는 Codex 서버**를 두고 여러 명령·백그라운드 작업이 공유.
- direct = 가볍고 단순 / 공유 런타임 = 지속·병렬 작업(위임·스레드·상태 조회)에 유리하며 필요 시 자동 기동.

### 차이 요약
| 구분 | 헤드리스 모드 | direct 모드 |
| --- | --- | --- |
| 무엇에 관한가 | **인터페이스** (대화형 UI 없이 1회 실행) | **실행/프로세스 모델** (상주 서버 없이 매번 직접) |
| 반대 개념 | 대화형(interactive) | 공유 런타임(shared runtime) |
| 한 줄로 | "어떻게 부르나" | "백엔드를 어떻게 관리하나" |

핵심: 둘은 **직교(orthogonal)** 하다. 예를 들어 `codex exec`는 **헤드리스이면서 direct**일 수 있다. 하나는 "UI 없이 한 방에", 다른 하나는 "상주 서버 없이 그때그때" — 서로 독립적인 이야기다.

## 5. 반복 개선 루프 — 5 → 0 PASS

픽셀아트 앱을 대상으로 돌린 결과:

```
1차:  5건 발견
2차(2건 수정): 2 해결, 3 남음 + 신규 1
3차(3건+aria 수정): 3 해결, 2 남음 → FAIL
4차(2건 정밀 수정): 2 해결, 0 남음 → PASS ✅
```

엄격한 평가자는 고친 것 안에서 **더 정밀한 문제**(정규식 자릿수까지!)를 파고든다. 자기검증만으로는 절대 5→0까지 못 갔을 것이다.

전후 확인은 세 층위로: **① `git diff`(코드) ② 로컬 서버(동작) ③ 재리뷰(평가)**.

## 6. 하네스를 스킬로 패키징

이 전체 하네스(CLAUDE.md 규칙 + 기술스택 + Codex 평가 루프 + 권한 설정)를 `webapp-harness-jek` 스킬로 묶었다.

- 스킬 = **폴더**(`SKILL.md` + `references/`), 프론트매터에 **`name`·`description` 필수**.
- `description`이 **트리거** — 상황과 맞으면 Claude가 자동 선택.
- 스코프: `.claude/skills/`(프로젝트) vs `~/.claude/skills/`(전역).

## 7. 세션 시작 시 읽는 설정 파일 총정리

| 범주 | 파일 |
| --- | --- |
| 지침 | `CLAUDE.md`(프로젝트/전역/`.local`), `AGENTS.md`, 메모리 |
| 설정 | `settings.json`(전역/프로젝트/`.local`), 관리자 설정 → 그 안의 `hooks` |
| 스킬·명령 | `skills/*/SKILL.md`, `commands/*.md` (전역/프로젝트/플러그인) |
| MCP·플러그인 | `.mcp.json`(프로젝트), `~/.claude.json`(전역) |
| 무시·환경 | `.claudeignore`, `.env`/`.env.local`, 셸 프로필 |

관통하는 원리: **스코프 3층(전역/프로젝트/개인) · 세션 시작 시 로드 · 점진적 공개 · 로컬 저장(git 제외)**.

## 실습하며 나온 질문들 (Q&A)

***Q). Codex의 direct 모드가 뭐야?***  
A). 명령마다 Codex를 직접 1회성으로 호출하는 가벼운 모드다. 반대로 공유 런타임은 백그라운드에 상주하는 서버로, 지속·병렬 작업(위임·스레드·상태 조회)에 쓰인다.

***Q). `--enable-review-gate`는 코드리뷰에만 적용돼, 아니면 모든 codex 명령에?***  
A). 둘 다 아니다. **Claude Code가 작업을 끝내려는 "종료(Stop) 시점"에 리뷰를 강제**하는 지속 설정이다. 개별 codex CLI 호출이 아니라 Claude의 마무리를 관문으로 막는다.

***Q). Google 로그인은 내부적으로 무슨 일이 일어난 거야?***  
A). OAuth 2.0 흐름이다. 브라우저 동의 → 인가 코드 → 토큰 교환 → 리프레시 토큰을 `~/.gemini/oauth_creds.json`에 캐싱. 이후 헤드리스 호출이 자동 인증된다.

***Q). `oauth_creds.json`을 복사하면 새 PC에서 재인증 없이 쓸 수 있어?***  
A). 대체로 된다(리프레시 토큰은 기기 종속이 아님). 단 비밀값이라 공유·커밋 금지, 만료·폐기 가능. 더 쉬운 정석은 새 기기에서 재로그인이다.

***Q). Gemini API 키는 어디서 받아?***  
A). Google AI Studio(aistudio.google.com/apikey)에서 발급. `GEMINI_API_KEY` 환경변수로 두면 된다. Public 저장소엔 절대 커밋 금지.

***Q). `codex-plugin-cc` 설치는 어떻게 해?***  
A). Claude Code에서 `/plugin marketplace add openai/codex-plugin-cc` → `/plugin install codex@openai-codex` → `/reload-plugins` → `/codex:setup`. 단 `/plugin`은 CLI(터미널)에서만 되고 VS Code 확장에선 안 된다.

***Q). 로컬 스킬을 다른 프로젝트에서도 쓰려면?***  
A). `~/.claude/skills/`(전역)로 복사한다. 단 경로가 특정 프로젝트에 종속적이면 일반화가 필요하다. 다른 컴퓨터는 git 미포함이라 수동 복사.

***Q). 스킬을 만들면 Claude Code가 어떻게 인지해?***  
A). 세션 시작 시 스킬 폴더를 스캔해 `SKILL.md`의 `name`·`description`을 등록한다. description만 상시 로드(트리거)되고 본문·references는 호출될 때 로드된다(점진적 공개). 새로 만들면 재시작해야 확실히 반영.

***Q). `SKILL.md`에 `name`·`description`은 반드시 있어야 해?***  
A). 그렇다, 둘 다 필수다. 특히 `description`은 "언제 쓰는가"를 정하는 트리거라 없으면 발동이 안 된다. `allowed-tools` 등은 선택.

## 마무리

오늘은 "AI가 만든 걸 다른 AI가 검증한다"는 구조를 실제로 돌려봤다. 반복 리뷰로 5건이 0건이 되는 걸 눈으로 보니, 왜 엔트로픽이 "별도의 엄격한 평가자"를 권하는지 납득이 됐다. 그리고 이 모든 절차를 스킬로 묶어두니, 다음엔 트리거 한 번으로 같은 품질을 재현할 수 있게 됐다.
