# 토큰 사용량과 clear, compact

세션이 길어지자 토큰 사용량이 걱정돼서, **왜 토큰이 커지는지**와 그걸 줄이는 두 명령 **`/clear`·`/compact`** 의 기능·차이를 파고들었다. 결론은 "매 턴 전체 대화를 다시 입력받기 때문에 길수록 비싸지고, `/clear`로 그 누적분을 내려놓으면 다음 턴부터 다시 가벼워진다"였다.

## 1. 토큰 사용량이 커지는 이유

LLM은 **기억이 없다.** 매 요청마다 "그때까지의 대화 전체"를 통째로 다시 입력받아 답을 만든다.

```
1번째 메시지  → 입력: [시스템 + CLAUDE.md + 메시지1]
10번째 메시지 → 입력: [시스템 + CLAUDE.md + 메시지1~9 전부 + 메시지10]
100번째      → 입력: [시스템 + CLAUDE.md + 메시지1~99 전부 + 메시지100]  ← 매번 이 큰 걸 재처리
```

즉 대화가 쌓일수록 **메시지 하나를 보낼 때마다 누적된 히스토리가 매번 딸려가서** 입력 토큰이 계속 커진다. 짧은 한마디도 뒤에 방대한 맥락이 붙어 비싸진다.

## 2. `/clear`의 기능

대화 히스토리를 **컨텍스트에서 통째로 버린다.** 다음 요청의 입력이 **기본값(baseline)** 으로 돌아간다.

```
/clear 직후 → 입력: [시스템 + CLAUDE.md + 메모리 + 스킬 목록 + 새 메시지]  ← 훨씬 작음
```

- 예(대략): 컨텍스트가 ~150K였다면 → `/clear` 후 ~10~20K baseline으로. 메시지당 토큰이 확 줄어든다.
- **삭제가 아니라 "치워두기"**: 이전 대화는 디스크(transcript `.jsonl`)에 그대로 남는다.
- CLAUDE.md·메모리·스킬·설정은 파일이라 **그대로 유지**(새 세션 시작 시 자동 재로드). 초기화되는 건 **대화뿐.**

### ⚠️ 오해 방지 — "환불"이 아니다

| 맞음 | 아님 |
| --- | --- |
| 앞으로의 메시지가 다시 싸짐 | 이미 쓴 토큰이 되돌아옴/환불됨 |
| 매 턴 딸려가던 누적 히스토리를 내려놓음 | 과거 사용량이 0이 됨 |

즉 **이미 소비한 건 소비된 것**이고, `/clear`는 **앞으로의 턴을 다시 가볍게** 만드는 것이다.

### `/clear` 후 baseline에 남는 것

0이 아니라, 세션 시작 시 로드되는 것들이 baseline을 채운다:

- 시스템 프롬프트·도구 정의
- **CLAUDE.md, 메모리(MEMORY.md), 스킬·명령 description**
- (상시 로드되는 "가벼운 색인"들 — 그래서 baseline이 작다)

## 3. `/compact`의 기능

대화를 **요약본으로 압축**해 공간을 비운다. 히스토리를 완전히 버리지 않고, 요약으로 줄여서 이어간다.

- `/clear`가 "통째로 버림"이라면 `/compact`은 "줄여서 유지".
- 자동 압축(auto-compaction)도 있어, 컨텍스트가 차면 알아서 요약해 이어간다.
- 단 요약이라 **디테일 손실**이 있을 수 있다.

## 4. `/clear` vs `/compact` 차이

| 구분 | `/clear` | `/compact` |
| --- | --- | --- |
| 히스토리 | **통째로 버림** | **요약본으로 압축**(일부 유지) |
| 결과 | baseline으로 리셋 | 줄어든 요약 컨텍스트 |
| 손실 | 대화 맥락 사라짐(파일엔 남음) | 요약 과정의 디테일 손실 |
| 언제 | 완전히 새 주제/토큰 리셋 | 맥락은 이어가되 공간만 확보 |

핵심: **완전히 새로 시작 = `/clear`, 맥락 이어가며 축소 = `/compact`.** 둘 다 이미 쓴 토큰을 환불하는 게 아니라, **앞으로의 턴을 가볍게** 만드는 것이다.

### 관련 개념 한눈에

| 방식 | 무엇 |
| --- | --- |
| `/clear` | 히스토리 **통째로 버림** → baseline으로 (요약 없음) |
| `/compact` | 히스토리를 **요약본으로 압축** → 일부 유지하며 축소 |
| 프롬프트 캐시 | 재전송분이 캐시에 있으면 `cache_read`로 **싸게** 처리(비용 완화) |

## 실습하며 나온 질문들 (Q&A)

***Q). `/clear`를 쓰면 이전에 대화했던 내용을 못 보는 건가?***
A). 현재 화면·Claude의 기억에선 사라지지만, **디스크에는 그대로 남는다**(`~/.claude/projects/.../<세션id>.jsonl`). 삭제가 아니라 활성 컨텍스트에서 내려놓는 것뿐이다. 다시 보려면 `/resume`으로 그 세션을 불러오거나 transcript 파일을 직접 열면 된다. `/compact`이 파일을 안 지우는 것과 같은 원리다.

***Q). 이전 대화가 보고 싶어서 `/resume`을 쓰면 토큰을 다시 크게 쓰는 거지?***
A). "보기만" 하느냐 "이어서 대화"하느냐로 갈린다. transcript를 **그냥 보는 것**(스크롤/표시)은 클라이언트가 파일을 읽어 보여줄 뿐이라 모델 토큰을 거의 안 쓴다. 하지만 `/resume` 후 **새 메시지를 보내 이어가면**, 그 대화 히스토리가 다시 컨텍스트로 로드돼 입력 토큰이 크게 든다(프롬프트 캐시로 일부 완화되지만 공짜는 아님). 그래서 뭔가 확인만 할 거면 resume로 보기만 하거나 transcript를 `grep`하는 게 싸다.

***Q). MEMORY.md 파일의 용도는 뭐고 언제 쓰이나?***
A). 개별 메모리 파일들의 **색인(목차)** 이다. 한 줄에 하나씩 "제목 + 요약"을 담는다. **세션이 시작될 때마다 컨텍스트로 로드**되어, `/clear`·새 세션·다른 날에도 Claude가 사용자·프로젝트에 대해 아는 것을 유지한다. 목차에서 관련 항목이 있으면 그 개별 메모리를 떠올려 활용한다. 색인만 상시 로드되고 개별 파일 전체는 아니라 가볍다(스킬 description만 상시 로드되는 절약 원리와 같다).

***Q). MEMORY.md의 물리적 위치는 어디야?***
A). `~/.claude/projects/-Users-gracej-Claude-my-blog/memory/MEMORY.md`. 폴더명 `-Users-gracej-Claude-my-blog`는 프로젝트 경로의 `/`를 `-`로 바꾼 인코딩이다. **프로젝트별로 분리**되어 이 프로젝트 세션에서만 로드되고, `~/.claude/` 아래라 로컬 저장(git 미포함)이다.

***Q). `/clear`를 하면 그동안 로드했던 CLAUDE.md·스킬·하네스는 유지되고 대화 내용만 초기화되는 거지?***
A). 맞다. CLAUDE.md·스킬·슬래시 명령·하네스 규칙·메모리는 전부 **파일(디스크)** 이라 그대로 있고 새 세션에서 자동 재로드된다. 초기화되는 건 **대화**뿐이다. 단, 대화 중 읽어들였던 파일 내용(예: `app.js`)은 컨텍스트에서 사라지므로, 필요하면 새 세션에서 다시 읽으면 된다(그때만 소량 토큰).

***Q). `/clear` 후 "토큰 리셋"이 된다는 의미를 더 자세히?***
A). LLM은 매 요청마다 전체 대화를 다시 입력받으므로, 길어질수록 메시지당 입력 토큰이 계속 커진다. `/clear`는 그 누적 히스토리를 내려놓아, 다음 요청의 입력을 baseline(시스템 + CLAUDE.md + 메모리 + 스킬 목록 + 새 메시지)으로 축소한다. 즉 **이미 쓴 토큰의 환불이 아니라, 앞으로의 턴을 다시 가볍게** 만드는 것이다. baseline이 0은 아니지만(상시 로드되는 색인들이 있음) 긴 대화보다 훨씬 작다.

## 마무리

토큰이 커지는 건 "모델이 매번 전체 대화를 다시 읽기 때문"이라는 원리를 알고 나니, `/clear`(버리기)와 `/compact`(요약하기)의 쓰임이 명확해졌다. 세션이 무거워지면 중요한 건 메모리·파일로 남기고 `/clear`로 리셋하는 게 가장 확실한 절약이다. 이 글도 그 리셋 직전에 남기는 기록이다.
