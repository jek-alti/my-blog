# 코드 탐색 기법부터 컨텍스트 엔지니어링까지 — 오늘 다룬 개념 총정리

오늘은 범위가 꽤 넓었다. 코드베이스를 뒤지는 세 가지 방식(grep·LSP·CodeSight)에서 시작해 회귀 방지 테스트 전략, 슬래시 커맨드와 PR 개념, Anthropic의 컨텍스트 엔지니어링과 context rot·KV-cache, Kent Beck의 증강코딩, 그리고 Claude Code와 Codex의 스킬·서브에이전트·훅 생태계 비교까지 이어졌다. 마지막엔 claude-code-lsps 플러그인 설치 과정을 직접 뜯어보며 marketplace add와 plugin install이 실제로 무슨 일을 하는지도 확인했다.

## 1. 코드 탐색 3방식: grep · LSP · CodeSight

| 방식 | 원리 | 강점 | 약점 |
|---|---|---|---|
| grep | 텍스트/정규식 매칭 | 설정 불필요, 범용적 | 오탐 많음, 다단계 왕복 필요 |
| LSP | 언어 서버가 사전 인덱싱한 심볼/타입 정보 질의 | 오탐 없는 정밀한 결과, 왕복 적음 | 언어 서버 구동 비용, 동적 언어에서 정확도 저하 |
| CodeSight류 | 저장소를 미리 스캔해 압축 지도(map) 생성 후 재사용 | 반복 질문에서 압도적으로 저렴 | 최신성 유지 위해 재인덱싱 필요 |

핵심은 "토큰 효율"이다. grep은 매번 텍스트를 새로 훑고 걸러내야 하지만, LSP는 언어 서버가 이미 검증한 결과를 그대로 받아 쓸 수 있고, CodeSight류는 한 번 만든 지도를 계속 재사용한다.

## 2. 회귀 방지 테스트 전략: 커버리지 모니터링

레거시 코드 전체를 100% 커버리지로 끌어올리는 대신, 실무에서 흔히 쓰는 절충안:

- **전체 커버리지 모니터링**: 추세만 감시 (절대치 강제 X)
- **새 코드엔 새 테스트**: diff/patch coverage — 이번 PR에서 바뀐 라인만 커버리지 검사 (Codecov `patch` 상태, SonarQube "Coverage on New Code")
- **커버리지 하락 방지**: ratchet(래칫) — 직전 빌드보다 낮아지면 실패, 올라가면 기준선 갱신

세 가지를 합치면 "과거 빚은 당장 안 갚아도, 새 빚은 안 지고, 전체 잔고는 나빠지지 않게" 관리하는 셈이다.

## 3. 슬래시 커맨드와 PR

- **PR(Pull Request)**: 브랜치 변경사항을 메인에 합치기 전 검토받는 요청. diff·리뷰어·CI 체크·머지 버튼으로 구성.
- **`/code-review`**: 정확성 버그 + 재사용/단순화 개선점, effort level(low~max) 조절, `--comment`/`--fix` 옵션. diff·PR 번호·브랜치·경로를 대상으로 지정 가능.
- **`/simplify`**: 버그는 안 보고 품질(재사용·단순화·효율)만, 발견 즉시 자동 적용.
- **`/security-review`**: 현재 브랜치의 미머지 변경사항을 보안 관점으로만 점검.

## 4. 컨텍스트 엔지니어링 (Anthropic)

"가능한 한 작은 고신호(high-signal) 토큰 집합으로 원하는 결과를 극대화하라"는 원칙 아래:

- 시스템 프롬프트는 "적절한 고도"로 (너무 하드코딩되지도, 너무 두루뭉술하지도 않게)
- 도구는 겹치지 않고 명확하게
- 예시는 엣지케이스 나열이 아니라 소수의 전형적 사례로
- **Just-in-time 검색**: 미리 다 로드하지 말고 가벼운 식별자로 필요할 때만
- **Compaction**: 한계에 가까워지면 요약 후 재시작 (핵심은 보존, 중복은 제거)
- **구조화된 메모**: 컨텍스트 창 밖에 영구 기록
- **서브에이전트**: 각자 깨끗한 컨텍스트에서 작업 후 압축된 요약만 반환

**Context rot**: 입력 토큰이 늘수록 모델의 회상 정확도가 떨어지는 현상 (Chroma, 2025). 18개 모델 실험에서 needle-question 유사도가 낮을수록, distractor가 많을수록 성능이 더 빨리 무너졌고, 놀랍게도 논리적으로 잘 짜인 글보다 문장을 무작위로 섞은 글에서 오히려 성능이 나았다.

**KV-cache hit rate**: "프로덕션 에이전트에서 가장 중요한 단일 지표". Claude Sonnet 기준 캐시된 입력 토큰은 $0.30/MTok, 캐시 안 된 건 $3.00/MTok — 10배 차이. 시스템 프롬프트 맨 앞에 초 단위 타임스탬프를 넣거나, JSON 키 순서가 비결정적이거나, 도구를 동적으로 추가/제거하면 캐시가 깨진다.

## 5. Kent Beck의 증강코딩과 TDD

증강코딩(augmented coding)은 "AI가 코드를 생성해도 사람이 직접 짤 때와 같은 품질 기준(깔끔함, 테스트, 커버리지)을 요구하는 태도"고, "바이브 코딩"(동작만 신경 쓰고 코드 자체는 신경 안 씀)과 대조된다. TDD는 이 증강코딩을 지탱하는 핵심 규율 — AI가 회귀를 자주 일으키기 때문에, 테스트가 AI를 올바른 방향으로 붙잡아두는 하네스 역할을 한다. 즉 둘은 경쟁 기법이 아니라 포함 관계다.

## 6. 플러그인 vs 스킬, 그리고 Codex와의 비교

- **스킬**: 재사용 가능한 작업 지침 자체 (`SKILL.md`)
- **플러그인**: 스킬+서브에이전트+커맨드+MCP를 묶어 배포하는 포장 단위, 마켓플레이스로 유통

Codex CLI도 2026년 들어 거의 같은 어휘(skill/subagent/command/hook/plugin)로 수렴했다. 서브에이전트는 `.toml`로 정의하고 최대 6개 동시 실행, 커스텀 프롬프트는 스킬로 통합되는 중, 훅은 아직 베타 단계. Codex만의 독자 요소로는 full-auto 모드의 "guardian 서브에이전트"(자동 승인/차단 판단)가 있다.

## 7. Frontmatter와 서브에이전트 구조

Frontmatter는 마크다운 파일 맨 위 `---`로 감싼 YAML 메타데이터 블록 — "이 파일이 뭔지"를 프로그램이 파싱하는 부분과 "실제 지침"인 본문을 분리한다. 실제 `code-reviewer` 서브에이전트 파일을 열어보니:

```yaml
---
name: code-reviewer
description: Reviews code for bugs, logic errors, security vulnerabilities...
tools: Glob, Grep, LS, Read, NotebookRead, WebFetch, TodoWrite, WebSearch, KillShell, BashOutput
model: sonnet
color: red
---
```

`tools` 필드에 `Edit`/`Write`/`Bash`가 빠져있는 게 "리뷰만 하고 코드는 안 건드린다"는 설계 의도를 그대로 강제하고 있었다.

## 8. LSP 플러그인 설치 단계별 의미

- **`marketplace add`**: github repo 통째로 clone, 카탈로그 등록만 함 (아직 아무 LSP도 활성화 안 됨)
- **`plugin install <이름>`**: 카탈로그 중 하나(예: vtsls) 골라서 `.lsp.json`의 실행 스펙(`command`, `args`, 확장자 매핑)을 Claude Code의 LSP 도구 백엔드에 배선
- **`npm i -g @vtsls/language-server typescript`**: 위 두 단계는 "vtsls를 쓰겠다"는 설정만 해둔 것이고, 실제 `vtsls` 바이너리 자체는 이 npm 명령으로 전역 설치해야 함. `typescript` 패키지는 vtsls가 감싸는 MS `tsserver`를 제공하기 위해 필요.

즉 "설정 등록"과 "실제 실행파일 설치"는 별개 단계였다.

## 실습하며 나온 질문들

***Q). 토큰 효율화 차원에서 grep 방식, LSP 방식, CodeSight 방식을 각각 설명해주고 방법적인 예시도 함께 설명해줘.***  
A). 세 방식의 원리·장단점을 표로 비교하고, 각각 `rg` 명령, LSP의 `textDocument/definition`/`references`, `codesight init`/`codesight .` 같은 실제 예시를 들어 설명했다.

***Q). 회귀방지 테스트 전략으로 커버리지 모니터링 - 새코드엔 새 테스트, 커버리지 하락방지 라는 전략을 쓴다고 하는데 자세히 설명해줘.***  
A). 전체 커버리지 추세 감시, diff/patch coverage 게이트(Codecov·SonarQube 예시), ratchet 메커니즘(의사 스크립트 포함) 세 축으로 나눠 설명했다.

***Q). /review에 대해 최근변경 코드를 PR 리뷰수준으로 점검 이라고 설명되어 있는데, PR에 대해서 설명해줘.***  
A). PR(Pull Request)의 정의, 구성요소(diff·리뷰어·CI체크), `gh` CLI 예시를 들고, "PR 리뷰 수준"이 diff coverage와 같은 맥락(변경분에 집중한 검토)임을 짚었다.

***Q). 슬래시 커맨드중 review, simplify, security-review 에 대해 설명해주고 예시를 들어줘.***  
A). 세 커맨드를 초점(버그+품질 / 품질만 / 보안만)과 자동수정 여부로 비교표를 만들어 설명했다.

***Q). 예를들어 내가 /review를 한다고 하면 /review 파일명 또는 /review 폴더명 이렇게 실행하면 되는건가?***  
A). 실제 커맨드 정의 파일을 찾아 읽어보니, VSCode 버튼용 SKILL.md(단순 diff 리뷰, 옵션 없음)와 마켓플레이스의 PR 전용 커맨드(gh 기반, 멀티 에이전트 신뢰도 채점) 두 구현이 서로 달라, 처음 설명한 effort-level/경로 인자 문법을 파일 근거로 확정할 수 없었다는 점을 정정했다.

***Q). Glob 패턴이 뭔지 알려줘.***  
A). `*`/`?`/`[...]`/`**`/`{...}` 등 기본 문법과, `*` vs `**`의 디렉토리 계층 차이를 예시로 정리했다.

***Q). /memory 커맨드에 대해 자세히 알려줘.***  
A). CLAUDE.md 편집 기능과 auto-memory(활성화/조회) 두 갈래로 구성되어 있고, 지금 세션에선 에디터를 여는 방식이라 VSCode 내장 환경에서 막혀 있음을 설명했다.

***Q). Kent Beck에 대해서 알려줘.***  
A). XP·TDD·JUnit·CRC카드·애자일 선언문 등 업적과, 2026년 "Still Burning" 팟캐스트·AI 시대 소프트스킬 발언 등 최근 근황을 정리했다.

***Q). 앤트로픽의 effective context engineering에 대해서 알려줘.***  
A). 프롬프트 엔지니어링과의 차이, context rot 문제의식, 시스템프롬프트/도구설계/예시/JIT검색/compaction/노트테이킹/서브에이전트 7가지 전략을 원문 기준으로 정리했다.

***Q). 컨텍스트 엔지니어링에서 KV-cache hit rate에 대해 알려줘.***  
A). KV-cache 기본 원리, Manus 사례의 100:1 입출력 비율과 Claude Sonnet 캐시/비캐시 10배 가격차, 캐시를 깨는 요인(타임스탬프·비결정적 직렬화·동적 도구 변경)과 안정화 방법을 정리했다.

***Q). context rot에 대해 설명해주고 앤트로픽에서 context rot을 최대한 줄일수 있는 방법론으로 어떤걸 제시하는지 설명해줘.***  
A). Chroma 기술 리포트의 실험 종류·발견(특히 무작위로 섞은 글이 더 잘 읽히는 반직관적 결과)과, Anthropic이 제시하는 7가지 완화 기법을 "무관한 토큰이 애초에 안 쌓이게 하는 구조적 해법"이라는 프레임으로 다시 엮었다.

***Q). Kent Beck의 증강코딩과 TDD는 서로다른 기법이야?***  
A). 경쟁 기법이 아니라 포함 관계 — 증강코딩은 상위 철학, TDD는 그걸 지탱하는 핵심 규율(가드레일)이라는 결론과 Beck 본인의 인용을 함께 정리했다.

***Q). plugin과 스킬의 차이점이 뭐야?***  
A). 스킬=콘텐츠, 플러그인=배포 포장 단위라는 핵심 차이를, 실제 파일시스템에서 확인한 `code-review` 플러그인의 `commands/`·`agents/` 구조로 뒷받침했다.

***Q). skill, subagent, command, hooks 등 클로드코드의 개념들이 codex agent에도 그대로 있는건가?***  
A). 2026년 기준 Codex CLI가 거의 같은 어휘로 수렴했음을 비교표로 정리하고, TOML 기반 서브에이전트 정의·guardian 서브에이전트 같은 Codex 고유 요소도 짚었다.

***Q). claude subagent의 마크다운+frontmatter에 대해 더 설명해줘, frontmatter가 뭔지 내가 잘 몰라.***  
A). frontmatter의 일반 개념(메타데이터/본문 분리)부터, 실제 `code-reviewer.md` 파일의 `name`/`description`/`tools`/`model`/`color` 필드 각각의 역할, 그리고 SKILL.md·커맨드 파일과의 필드 스키마 차이까지 실물 예시로 설명했다.

***Q). claude-code-lsps를 설치할때 marketplace를 add한다음에 설치하던데, 이 동작들의 의미에 대해 단계별로 알려줘.***  
A). 실제 `known_marketplaces.json`과 플러그인 폴더를 열어보고, marketplace add(카탈로그 전체 clone)와 plugin install(하나 골라 `.lsp.json` 스펙 배선) 두 단계의 차이를 실물 파일 기준으로 설명했다.

***Q). npm i -g @vtsls/language-server typescript 명령어가 어떤 동작을 하는것인지 설명해줘.***  
A). `-g`(전역 설치), `@vtsls/language-server`(vtsls 바이너리 본체), `typescript`(vtsls가 감싸는 tsserver 제공) 세 부분의 역할과, 이게 앞선 플러그인 설정 단계가 채우지 못한 "실행파일 자체 설치" 공백을 메우는 단계임을 설명했다.

## 마무리

오늘은 도구 하나하나를 겉핥기로 넘기지 않고, 실제로 설치된 플러그인 파일과 마켓플레이스 등록 정보를 직접 열어 근거를 확인하며 답을 정정해 나간 과정이 특히 남는다. "설명이 그럴듯해도 실제 파일과 다를 수 있다"는 걸 `/code-review` 사례에서 직접 확인한 게 오늘의 가장 큰 소득이었다.
